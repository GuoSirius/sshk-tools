## 二、当前 Bug 修复清单（#1–#8 具体规格）

### #1 css 另存为弹框流程（R14.3 重排）
- 现状（见截图）：只有「目标 css 目录」+「新文件名」两步，缺「系统/自定义」来源选择。
- 修订弹框步骤：① **来源**（系统内容 / 自定义内容库，分组切换）→ ② **目标 css 目录**（按来源过滤的树形下拉，含自身所在目录）→ ③ **新名称**（目录改名 / 文件改名，冲突实时校验）。
- 携带内容说明保留（目录下全部 css 文件，目录名恒为 css，文件名不变，冲突询问）。

### #2 表单 label 错位（通用修复）
- 根因：label 列宽不足，长文本如 `code（目录名）` 换行后破坏各行列对齐。
- 修复：label 列设 `min-width` + `white-space: nowrap` + `text-overflow: ellipsis`（hover 出全称），或改为 label 在上、控件在下的堆叠布局（窄屏友好）。**全局表单组件统一改**，不只另存为弹框。

### #3 重命名语义 + 左树命名规范（R13 关联，重要规范）
- **重命名对象 = 目录名（磁盘目录）**，不是 code、也不是元数据里的显示名。
  - 例：`elabscience/fragment/banner` 重命名 → 改 `banner` 目录名；`banner` 内的 `meta.yaml` 的 `code`/`name` 不动（除非用户另在元数据里改）。
- **取消不再报错**：当前 rename 取消仍弹错误提示，需修；取消应静默返回。
- **左树展示规范**（统一所有节点）：`目录名 + （元数据 name / code，若有的话）`。
  - 品牌：`elabscience（Elabscience）`；族：`banner（顶部横幅）`；版本：`default`；css 目录：`css`。
  - 显示名取元数据 `name` 优先，无则回退 `code`，再无则仅目录名。

### #4 元数据保存实时反馈左树（树响应式）
- 根因推测：左树节点 label 在加载时快照，元数据保存后未触发树节点重算。
- 修复：元数据保存成功后，发事件/调 store 更新对应树节点的展示名（目录名不变、name/code 变则刷新括号内容），无需整树重建。
- 与 #3 命名规范共用同一「节点展示名计算函数」。

### #5 另存为目标按类型过滤（R14 扩展）
- 模板族/版本另存为：目标选择**只列模板类目下的落点**（品牌→模板类目→族/版本）；
- 片段族/版本另存为：目标**只列片段类目下的落点**；
- 避免把片段存进模板、反之亦然（用户硬约束）。

### #6 右键菜单 click-outside 关闭
- 全局右键菜单组件加 `document` 的 `mousedown`/`contextmenu` 监听：点击菜单外任意区域（含左树其他节点、主区）即关闭；打开新右键菜单时先关旧的。

### #7 删除失败 ENOENT（fragment\banner.css）
- 错误：`lstat '.../elabscience/fragment/banner.css'` —— 把「类目目录」误当「版本目录」去拼 `banner.css`（版本级内联 css 文件名），但类目下本无该文件。
- 修复：删除路径拼接须按节点层级正确推导（类目层无 style.css；版本层才有），并先 `exists` 再 `lstat`/`unlink`，缺则跳过不报错。

### #8 拖拽可见性（FieldSchemaDesigner）
- 用户看不到字段拖拽生效：需确认 ① 拖动手柄（`.handle`）是否渲染、② `VueDraggable` 是否真绑定 `v-model="fields"`、③ 只读/非设计态是否禁用了拖拽。
- 修复：设计态显式显示 `⋮⋮` 手柄 + `cursor: grab`；保存即写回 `meta.yaml` 的 `fields` 顺序；非设计态 `:disabled="true"` 并去掉手柄。

## 三、统一组合引擎（核心架构 · 决策点 A）

> 这是 v6 最关键的新架构。把「片段预览 / 模板预览 / 邮件编辑」三处的渲染逻辑抽成一个引擎，输入一致、输出一致，行为天然一致。

### 3.1 引擎定义
```
compose(input: ComposeInput): Promise<HtmlString>
ComposeInput = {
  template:    { brand, templateRef, versionRef, njk, cssChain }   // 模板（含其 css 就近链）
  placements:  FragmentPlacement[]                                  // 片段摆放（见 3.2）
  data:        Record<string, any>                                  // 字段数据（示例 or 真实）
  cssChain:    CssSource[]                                           // 参与渲染的 css（模板链+片段链+选中）
}
FragmentPlacement = {
  fragmentRef, versionRef,
  slot:        string,        // 落入模板的哪个插槽/区块
  order:       number,        // 同槽内的顺序
  repeat:      number,        // 出现次数（默认 1）
}
```
- 处理链固定：**njk 渲染（模板套片段）→ juice 内联 CSS（合并 cssChain）→ html-minifier 压缩 → 输出 HTML**（正是 #10 要求的 njk+juice+minify）。
- 预览即把输出 HTML 灌进 `<iframe>`（沙箱）；导出/生成邮件即把 HTML 落盘/存库。

### 3.2 三个消费场景（统一映射到引擎）
| 场景 | template | placements | data | 备注 |
|---|---|---|---|---|
| **① 片段预览**（#9） | 下拉选的「宿主模板」 | `[{本片段, slot:main, repeat:1}]` | 片段自身 sample | 下拉 = 品牌内未排除黑白名单的模板 |
| **② 模板预览**（#11） | 当前模板 | 用户在沙盒里摆的片段 | 各片段 sample | 复用 ③ 的编辑器（demo 模式） |
| **③ 邮件编辑**（#10） | 选的模板 | 用户设计的片段布局 | 真实表单数据 | 最终生成邮件 |

→ **② 与 ③ 是同一个编辑器**，仅数据来源（sample vs 真实）和「是否落库生成邮件」不同。这就是 #11「行为高度一致」的落地方式。

### 3.3 模板插槽机制（✅ 已拍板：B1 meta 声明 blocks）

模板如何声明「片段可以放哪」→ **B1：模板 meta.yaml 声明 `blocks:`**。具体契约：

```yaml
# 模板 meta.yaml
blocks:
  - { key: header, label: 头部 }
  - { key: body,   label: 正文 }
  - { key: footer, label: 底部 }
```

- 渲染契约：引擎把每个 placement 的片段先用**其自身数据**渲染成 HTML，按 `block` 分组、组内按 `order` 排序、`repeat > 1` 重复追加，得到 `blocks = { header: html[], body: html[], ... }` 注入模板 njk 上下文。
- 模板 njk 输出：`{% for html in blocks.header %}{{ html | safe }}{% endfor %}`（片段 HTML 需 `| safe` 关自动转义）。
- placement 的 `block` 只能选模板 `blocks:` 声明过的 key，引擎校验，未声明即报错。
- 片段黑白名单 policy 在「可选片段清单」处过滤（复用 `policyAllows(fragment, template)`）。

## 四、片段预览（✅ 已拍板：与模板预览统一，**不加独立下拉**）

- 片段「预览」tab 不再做「独立简化预览 + 宿主模板下拉」，而是**直接复用统一组合编辑器**（与 §五模板预览、§六邮件编辑同一个）：
  - 进入时预置一个 placement = 当前片段（block 默认取模板第一个 block，可改）；
  - 宿主模板在组合编辑器内选择（范围 = 片段所属品牌下、未被该片段 policy 排除的模板版本）；
  - 模板 css + 片段 css 就近链合并，看到真实组合效果（#9 诉求完全覆盖）。
- 好处：片段预览 / 模板预览 / 邮件编辑三处行为 100% 一致，只维护一套 UI（#11 的落地方式）。

### 6.2 新建 / 编辑页（分步）

## 七、左树规范（#3/#4 关联，落地统一命名与响应式）
- **展示名函数**（全局唯一）：`display(node) = dirName + (meta.name ?? meta.code ? '（'+that+'）' : '')`。
- **重命名**只改 `dirName`（磁盘目录），触发树节点 key 稳定（用绝对路径做 key，改名后路径变 → 需保留 nodeId 映射或用旧路径定位后重渲染）。
- **元数据保存**→ 发 `tree:nodeMetaChanged(nodePath)` → store 刷新该节点括号内容（name/code 变则更新，dirName 不变不动）。
- 以上与 #3/#4 修复共用同一套逻辑，避免重复实现。

## 十一、R24 内容管理统一重构（系统自带 + 自定义 双顶层合并，2026-11-15）

### 动机
- 系统自带与自定义内容**逻辑完全一致**，仅「权限」与「落盘位置」不同；此前拆成两个菜单 + 两个页面（SystemPage / CustomLibraryPage），导致重复实现、UX 不一致、反复返工。
- 合并为**一颗树 + 一个页面**，统一交互；底层存储保持分离（见硬约束）。

### 硬约束（用户澄清，不可违反）
> 虽在一棵树里显示 / 操作，但**生成 / 落盘位置必须按原约定分开，不得串门**：
> - **系统自带**（`source=system`）：写**系统文件根**（`resolveEdmRoot()`，assets 目录，维持现状）；仅 dev / `app.developerMode` 可写（门控 = `systemEditable()`）。
> - **自定义**（`source=custom`）：写**自定义文件根 `custom-edm`**，位置按工具部署形态确定——**内建发布（packaged）** 落到 `userData/edm-custom`，**外置安装（dev）** 落到与系统根对应的可写位置（如 `edmRoot` 同级 `edm-custom`）；**不与系统根同位置**（两者可写时机不同）；内部组织结构与系统根**完全一致**。始终可写，不区分 dev/build。
> - 两者**均为文件落盘**（自定义也落文件，2026-11-15 用户追加「自定义最好也能落文件」），差异只在目录与编辑权限；任何写操作**必须落到各自正确的根，不得串门**。
> - 自定义**可纯文件落盘、不依赖 DB**（用户确认）；NeDB 自定义实体是否保留为邮件编辑器索引见待确认 #4。

### 菜单与文件
| 项 | 现状 | 变更 |
|---|---|---|
| `tool.manifest.json` menus | `mails / system / library / config` | 删除 `library`；`system` → `content`（label「内容管理」）；顺序 `邮件管理 → 内容管理 → 工具配置`，默认 `entryRoute=mails` 不变 |
| 页面文件 | `pages/SystemPage.vue` | 重命名为 `pages/ContentManagePage.vue`（文件名与菜单语义对应） |
| `EdmStudioPage.vue` | 映射含 `library→CustomLibraryPage` | 删除 `library` 映射；`content→ContentManagePage` |

### 左树结构（双顶层，自定义在上、系统自带在下）
```
内容管理
├─ 自定义（source=custom，NeDB）            ← 旧 CustomLibraryPage 树
│   └─ 品牌 → 片段/模板（类目）→ 族 → 版本
└─ 系统自带（source=system，文件域）        ← 旧 EDM 树（原顶层「EDM」改名）
    └─ 品牌 → 片段/模板（类目）→ 族 → 版本 + css 目录
```
- 下层结构（品牌 / 类目 / 族 / 版本 / css）保持现状，**不动**。
- **默认全部折叠**（去掉 `default-expand-all`），由用户自行展开。
- 每个 `TreeNode.data` 增加 `source: 'system' | 'custom'` 判别字段，驱动读写分支。
- 结构差异（已声明）：自定义无文件域，故**不显示 css 目录子树**；其样式直接走版本 inline css（样式 tab 编辑 `source.css`）。系统自带保留 css 目录分支。

### 右侧详情（统一五 tab）
元数据 / 示例数据 / 预览 / 源码 / 样式 —— 顺序与功能同现状；所有读写按 `source` 分支：

| 操作 | source=system | source=custom |
|---|---|---|
| 读元数据 | `content:readFile(systemRoot, meta.yaml)` | `content:readFile(customRoot, meta.yaml)` |
| 写元数据 | `content:writeFile(systemRoot, ...)` | `content:writeFile(customRoot, ...)` |
| 写示例数据 | sample.yaml（文件） | sample.yaml（文件） |
| 写源码 | source.njk（文件） | source.njk（文件） |
| 写样式 | style.css + css 目录分支 | style.css + css 目录分支（自定义根同样支持 css 目录） |
| 预览 | `system:render`（组合 / 单渲） | `system:render`（同一组合引擎，selector 指向 customRoot） |
| 可编辑判定 | `canEditSystem`（dev/developerMode） | 恒 `true` |
| 邮件编辑器索引 | 系统播种 | 自定义根播种 → NeDB `origin=custom`（文件为真相源） |

> 编辑门控：节点可编辑 ⟺ `source==='custom' || canEditSystem`；只读时隐藏一切编辑 UI（沿用现有逻辑）。

### 右键菜单（统一顺序 + 新增项）
**规范化显示顺序（所有节点通用）**：复制 → 粘贴 → 删除 → 重命名 → 另存为 → 新建。
各节点按可用项在该顺序内筛选渲染；「新建」下挂上下文相关子项（见待确认）。

| 节点 | 菜单项（按规范顺序；复制/粘贴仅 css 支持，实体节点不出现） |
|---|---|
| 根（自定义 / 系统自带） | 新建品牌 |
| 品牌 | 新建品牌（同级）、新建片段族、新建模板族、另存为、重命名、删除 |
| 片段类目 | 新建片段族、重命名、删除 |
| 模板类目 | 新建模板族、重命名、删除 |
| 片段族 | 新建片段（同级族）、新建版本、另存为、重命名、删除 |
| 模板族 | 新建模板（同级族）、新建版本、另存为、重命名、删除 |
| 版本 | 另存为、重命名、删除 |
| css 目录 | 复制、粘贴、另存为、新建样式（原「新建文件」改名）、重命名、删除 |
| css 文件 | 复制、另存为、重命名、删除 |

> 「新建」逐个对应原则（用户拍板）：品牌→新建品牌、片段→新建片段、模板→模板；族额外加「新建版本」。

- **另存为（自定义 / 系统自带 节点通用）**：
  - 系统自带节点 → 双来源：系统内容新副本 / 派生到自定义内容库（旧行为）。
  - 自定义节点 → 同样「基于此新建一个」（NeDB 内新实体），**且同样可选派生到 系统内容 / 自定义内容库**；能否写系统内容取决于 dev / `app.developerMode` 门控（与系统自带编辑权限一致）。
  - 目标落点按类型过滤（片段→片段类目/族，模板→模板类目/族），沿用 R14 逻辑。
- **粘贴**：仅 css 目录 / 文件支持，且**不可跨 source**（自定义无文件域）。
