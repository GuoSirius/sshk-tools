# 上传能力规划（R26，2026-11-15 定稿 → 同日全量落地）

> 类比模型（Model）范式：一次实现 + 一处配置 → 应用本身可用 + 所有工具只选即用。
> 上传（Upload）按同一思路做成**应用级共享能力**：一次实现 + 多 profile 配置，所有工具直接复用，不各做一套。
> **状态**：T1–T8 全部落地（B1/B4/B5/B7/B8，commit `e63def9` / `9021b69` / `d9f4119` / `87c79d3` / `6443de2`）。实现纪要见 §八；
> 用户复核轮次（12 项 + N1–N10）已全部处理，见 **§九**，其中 V7/V8/V9 等真实链路仍待 dev 实跑。

## 一、关键设计决策（本次细化，已拍板）

| 上传目标 | 配置形态 | 工具侧使用 |
|---|---|---|
| **本地目录** | 极简：仅一个**默认目录**（全局） | 工具可单独覆盖本地位置；无需 profile |
| **FTP / SFTP（合并为「远程 profile」）** | **多个命名 profile**，每个独立连接信息（`protocol` 区分 ftp/sftp；主机/端口/用户/密码/远程目录/被动模式） | 工具选某个 profile + 覆盖「远程目录」等非固定信息 |
| **云存储** | **多个命名 profile**，可同云多账号（如阿里云 OSS 主账号 / 子账号）、不同云混排 | 工具选某个 profile + 覆盖「bucket / 文件目录 / 位置」等个性化项 |

> 核心变化：**从「单一 FTP + 单一云」改为「远程(ftp/sftp) 多 profile + 云多 profile」**。连接信息在全局一次性预设，工具只选 profile 并填少量个性化字段。

## 二、数据模型

### 2.1 全局上传配置（app settings，由「上传配置工具」管理，密钥走 safeStorage）

```yaml
upload:
  local:
    defaultDir: "~/edm-out"            # 单一默认本地目录
  remote:                              # FTP / SFTP 合并为「远程 profile」，protocol 区分
    profiles:
      - id: ftp-prod
        name: "生产 FTP"
        protocol: ftp                  # ftp | sftp
        host: "192.168.1.10"
        port: 21                       # ftp 默认 21，sftp 默认 22
        username: "..."
        password: "<safeStorage>"
        remoteDir: "/edm/out"
        passive: true                  # 仅 ftp 生效
      - id: sftp-bastion               # 可任意增删，同结构 protocol: sftp
        ...
    defaultId: ftp-prod
  cloud:
    profiles:                          # 多个命名云配置，可同云多账号
      - id: oss-main
        name: "阿里云 OSS-主账号"
        provider: aliyun-oss
        region: "oss-cn-hangzhou"
        endpoint: "oss-cn-hangzhou.aliyuncs.com"
        bucket: "edm-prod"
        accessKeyId: "..."
        accessKeySecret: "<safeStorage>"
        baseUrl: "https://cdn.example.com"
      - id: oss-sub                    # 同云不同账号
        name: "阿里云 OSS-子账号"
        provider: aliyun-oss
        ...
      - id: cos-marketing
        name: "腾讯云 COS-营销"
        provider: tencent-cos
        ...
    defaultId: oss-main
  validation:                           # 全局默认校验，工具只能收紧
    accept: [".png", ".jpg"]
    maxSize: 5242880
```

> **实际落盘**：`app.upload.*` 存 `settings.json`（不含任何密钥）；密钥按 profile id 存 `secrets.bin`（safeStorage），ID 形如 `app:tool:upload-config:r1`，渲染层只拿 `hasSecret` 布尔值。归一化纯函数在 `packages/shared/src/upload-config.ts`（`normalizeUploadConfig` / `resolveUploadTool` / `listUploadProfiles` / `pickRemoteProfile` / `pickCloudProfile`），5 项单测覆盖。

### 2.2 工具级 configGroup `upload`（各工具 SettingsPage 渲染）

```yaml
upload:
  targetType: "cloud"        # local | remote | cloud
  profileId: "oss-main"      # 选中全局 profile；省略则用对应 defaultId
  overrides:
    remoteFolder: "/2026/campaign"   # 远端服务器位置覆盖（映射到 Provider 的 remotePath）
    bucket: "edm-prod-2"              # 云 bucket 覆盖
    prefix: "mail/"                  # 云对象 key 前缀 / 目录
    localDir: "D:/edm-out"            # 本地目录覆盖（type: dir）
  validation:
    accept: ".png,.jpg"               # 逗号分隔字符串，只可收紧
    maxSize: 1048576                  # 字节，只可更小
```

| 实现要点 | 说明 |
|---|---|
| 动态 profile 下拉 | `ToolConfigField.optionsSource: 'upload:all' \| 'upload:remote' \| 'upload:cloud'`；宿主 `SettingsPage.vue` 在 load 时调 `window.api.upload.profiles()` 生成选项，避免 manifest 写死 |
| 远端位置字段名 | 用 `remoteFolder`（`type: string`）：`check:contract` 要求路径类字段用 `dir`/`file`，但远端服务器位置不是本机目录，不能弹本机目录选择器；main 侧 `resolveUploadTool` 兼容 `remotePath` / `remoteFolder` 两个键 |
| 校验不能放宽 | 工具未设限的字段必须是 `undefined`（不是空数组 / 0），否则 `mergeValidation` 会把「空交集」当成更严规则而抹掉全局白名单 |

## 三、Provider 架构（Upload Service 内核）

- **位置**：`packages/upload-core`（新建共享包，与 `llm-gateway` 平级），由桌面端 main 进程持有 provider 实例（生命周期同模型服务）。
- **暴露方式**：main 进程经 IPC 暴露 `upload:single` / `upload:batch`（带进度事件），渲染层经 `window.api.upload.*` 调用，不直接持密钥。
- **统一能力**：单文件 / 批量上传（**并发控制**）、进度回调、失败重试、格式白名单 + 大小上限校验（**全局默认 + 工具可收紧**）、密钥运行时从 safeStorage 解析。

```ts
interface UploadProvider {
  type: 'local' | 'remote' | 'cloud'
  upload(file: LocalFile, ctx: UploadContext): Promise<UploadResult>   // { url, key/remotePath }
  uploadBatch?(files: LocalFile[], ctx: UploadContext): Promise<UploadResult[]>
}
```

- **Provider 实现**：
  - `LocalUploadProvider`：写本地目录，返回 `file://` URL。
  - `RemoteUploadProvider`：用 `basic-ftp`(ftp) / `ssh2`(sftp)（成熟包），按 profile 的 `protocol` 路由连接。
  - `CloudUploadProvider`：按 provider 路由官方 SDK——首期落地 `ali-oss`(阿里云)，其余厂商**明确抛错**（P3：不预装 SDK，只留扩展点）。

| 宿主 IPC 通道 | 用途 |
|---|---|
| `upload:single` / `upload:batch` | 单文件 / 批量上传，入参 `{ toolId, name, size, mime, source? | dataUrl? }` |
| `upload:progress` | main → renderer 进度推送（沿用 `update:state` 范式） |
| `upload:config:get` / `upload:config:set` | 读写 `app.upload.*`（不含密钥） |
| `upload:profiles` | 只读 profile 清单，供工具配置页动态下拉 |
| `upload:secret:set` / `upload:secret:state` | 写 safeStorage / 只回「是否已配置」 |

### 9.1 cpu-features 编译可行性结论（复核项 6）

| 维度 | 结论 |
|---|---|
| 它是谁引入的 | `ssh2` 的 **optional** 依赖，只在 `ssh2/lib/protocol/constants.js` 里以 `try { require('cpu-features')() } catch {}` 探测 CPU 指令集加速，用于协商加密算法；失败会回退纯 JS 探测 |
| Windows 能否编译 | **能**，但需要 VS Build Tools（C++ 桌面工作负载）、Python、node-gyp，并且必须针对 Electron 的 ABI 用 `electron-rebuild` 重编，产出 `build/Release/cpufeatures.node` |
| 值不值得 | **不值得**。① 只是可选加速，不影响 SFTP 功能正确性；② 包内 `../build/Release/*.node` 是相对路径，rolldown 静态解析会因文件缺失直接构建失败；③ `electron-builder.yml` 排除 `node_modules/**`，原生二进制需额外 `asarUnpack` + `extraResources` 白名单和多平台产物分发；④ 当前 `allowBuilds:false` 是刻意规避 Windows 原生编译链 |
| 决定 | **维持构建期 shim**（`electron.vite.config.ts` alias → `src/main/stubs/cpu-features.cjs`），零运行时依赖、SFTP 走纯 JS 回退 |
| 若将来确实要编译 | 需用户自行执行（AI 不代跑安装）：安装 VS Build Tools → `pnpm approve-builds cpu-features`（或 `allowBuilds` 放开）→ `pnpm exec electron-rebuild -f -w cpu-features`；随后移除 alias，并为打包产物补 `.node` 分发配置。**建议先实测性能收益再决定** |
