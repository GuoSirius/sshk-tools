## 二、依赖方向（D37）

| 方向 | 是否允许 | 实现 |
|---|---|---|
| 应用 → 工具（硬编码工具 id / 页面 / 图标 / 默认配置） | ❌ 禁止 | 宿主只认 `tool.manifest.json` 契约，构建期自动发现 |
| 工具 → 应用能力（config / repository / IPC / LLM / safeStorage / 本机 OCR） | ✅ 允许 | `ToolHostCapabilities` 注入插件 deps |
| 工具 → 工具（默认） | ❌ 默认禁止 | 清单 `dependsOn: []`；`check-boundaries.mjs` + ESLint 卡静态引用 |
| 工具 → 工具（显式声明硬依赖） | ✅ 可选 | 设置中心可配，依赖不可见时一并隐藏；软 `configDeps` 只预警 |
| 单个工具加载失败 / 禁用 | 不影响宿主与其它工具 | 插件逐个 `try/catch`；失败只标 `loaded=false` 并注册拒绝 handler |

**关键修复**：插件 main 入口早期是「一堆具名导出」，加载器曾按「随便找一个函数」挑注册函数，
会误挑 `parseDatasource` 导致 badge/edm 的 IPC 一个都没注册且**不报错**。
现在契约收紧为 **`src/main/index.ts` 必须 `export default` 注册函数**（或具名 `register`），
找不到就判定该插件加载失败并在设置中心显示原因。

## 三、工具包契约：放进 `tools/` 即零改动接入（D39 / D40）

### 目录约定

```
tools/<id>/
├── package.json               # name = @sshk/<id>
├── tool.manifest.json         # 唯一清单（目录名必须 = manifest.id）
├── assets/icon.svg            # 工具自己的图标（icon=auto 时启用）
├── src/
│   ├── index.ts               # 可选：包入口（别名自动发现）
│   ├── main/index.ts          # 可选：主进程插件，默认导出注册函数
│   └── renderer/*Page.vue     # 可选：渲染页，构建期自动发现
└── scripts/                   # 可选：本机适配器（如 PaddleOCR）
```

### `tool.manifest.json` 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` / `description` | string | 卡片元数据；可由 `app.toolOverrides.<id>` 覆盖 |
| `category` | `string \| string[]` | 主分类或**多个分类** |
| `tags` | `string[]` | 附加标签，与 category 合并去重为 `categories[]` |
| `icon` | string | `auto` = 工具包自带 `assets/icon.svg`；也支持 http(s) / data URI / `default`；无效一律回退系统默认四色图标 |
| `configLayout` | `single \| tabs \| menu` | 工具配置布局；内置工具统一 `single`（一页卡片） |
| `menus` | `ToolMenu[]` | 左侧功能菜单，支持任意层级 `children` |
| `configGroups` | `ToolConfigGroup[]` | 工具自有配置项，只读写 `tools.<id>.*` |
| `defaults` | object | 工具默认配置，宿主启动时 `mergeToolDefaults()` 自动合并 |
| `plugin` | `{ main, renderer, channels, source }` | 插件入口与专属 IPC 通道白名单 |
| `dependsOn` | `string[]` | 硬依赖，默认 `[]`；运行时可在设置中心改 |
| `configDeps` | `ToolConfigDependency[]` | 软依赖，只读展示 + 缺失预警 |
| `requiredGrant` | string | 权限要求，如 `tools.restricted`（未配访问密钥则隐藏） |
| `enabled` | boolean | 默认启用状态 |

### 宿主自动发现

| 位置 | 机制 | 产物 |
|---|---|---|
| 主进程 | `import.meta.glob('../../../../tools/*/tool.manifest.json')` + `*/src/main/index.ts` | `MANIFESTS` / `MAIN_LOADERS` |
| 渲染层 | `import.meta.glob('../../../../tools/*/assets/icon.svg', { query: '?raw' })` + `*/src/renderer/*Page.vue` | `TOOL_ICONS` / `RENDERER_LOADERS` |
| 构建配置 | `electron.vite.config.ts` 扫描 `packages/*` + `tools/*` 的 `package.json` 动态生成 alias 与 `externalizeDeps` 白名单 | 新工具无需改 alias |
| 测试配置 | `vitest.config.ts` 同样动态生成 alias | 新工具无需改测试配置 |

> 图标用 `?raw` 取 SVG 源码再内联成 data URI，规避 Electron `file://` 下相对资源路径失效；
> 开发态与安装包表现一致。

### PaddleOCR 接入（#13 可行性结论：可以）

- 已落地：同一套 `parseVisionResult` 接收「JSON 数组 **或** 带表头 CSV」，云端与本机输出结构完全一致；
  宿主提供 `runLocalOcr` 执行本机命令，工具包自带 `paddleocr_adapter.py` 参考模板（兼容 PaddleOCR 3.x `predict()` 与 2.x `ocr()`）。
- 配置示例（`vision.paddleCommand` / `vision.paddleArgs`，**必须绝对路径**，打包后 cwd 不是仓库根）：
  `D:/Anaconda3/python.exe` + `D:/workspace/code/sshk-tools/tools/badge-studio/scripts/paddleocr_adapter.py {image}`
- **待用户确认**：本机 Python 解释器绝对路径、PaddleOCR 实际版本与调用方式、截图版式（链接与点击数是否同一行、是否有千分位 / 合计列）。
  适配器 `rows_from_lines()` 是版式相关的参考实现，需要按真实截图校准。
- 识别结果一律先回填 CSV 供人工校对，不直接进生成链路。

## 七、IDE 红波浪线（#5 / #18）与刷新机制（#10）

### 7.1 关键判断：CLI 是干净的，红的是 IDE 语言服务

三套 tsconfig 全部实测 0 错误：`tsc -p tsconfig.base.json`、`tsc -p tsconfig.json`、`tsc -p apps/desktop/tsconfig.json`。
所以截图里的 `找不到模块 'vue' / 'element-plus' / '@sshk/ui-kit'`、`ImportMeta 上不存在属性 glob`、
`参数 group 隐式具有 any 类型` 不是代码错误，而是 **IDE 的 TS Server / Volar 没挂到正确项目，或仍在用旧推断项目缓存**。
`ssshk: Unknown word` 则完全不是 TS，是拼写检查插件（cspell）报的。

证据：根 `node_modules` 里**没有** `vue` / `element-plus` / `vite`，它们只存在于 `apps/desktop/node_modules`；
一旦 IDE 把文件挂到「以仓库根为基准的推断项目」，裸包解析与 `vite/client` 类型就会全丢。

### 7.2 仓库里已经落好的配置（提交进 Git，换电脑自动生效）

| 文件 | 作用 |
|---|---|
| `tsconfig.base.json` | `"@sshk/*"` 通配 paths 覆盖 `packages/*` 与 `tools/*`；新增 `"electron"` 显式指向 `apps/desktop/node_modules/electron/electron.d.ts`，让根项目也能解析 `electron` 类型 |
| `apps/desktop/tsconfig.json` | `types: ["node", "vite/client"]` **显式加载**，不依赖文件顶部的三斜线引用；`include` 显式列出 `src/**/*.vue` |
| `tsconfig.json`（根） | 只 include `packages / tools / scripts`，**刻意排除 apps**，避免 Volar 在「根项目」和「desktop 项目」之间选错造成 `.vue` 全红 |
| `.vscode/settings.json` | `typescript.tsdk` 指向工作区 TS；关闭 `enableProjectDiagnostics` 噪音；`eslint.workingDirectories`；`cspell.words` |
| `.vscode/extensions.json` | 推荐 `Vue.volar`（Vue - Official）+ ESLint；排除老的 `vscode-typescript-vue-plugin` |
| `cspell.json` | 项目术语词典（sshk / ulid / nedb / snapdom / paddleocr / agnes / apihub …），消除拼写类波浪线 |
| `.gitignore` | `.vscode/*.local.json` 忽略个人本机覆盖，团队共享配置照常提交 |

> 已移除 `vue.server.hybridMode: false`：现代 Volar 默认混合模式由 TS Server 管 `.ts`、Volar 管 `.vue`，
> 强制 takeover 反而可能让 `.ts` 的 `vite/client` 类型加载失效。

### 7.3 你需要做的操作（按顺序，缺一步都可能还红）

| 步 | 操作 | 为什么 |
|---|---|---|
| 1 | **确认 VS Code 打开的是仓库根目录 `D:/workspace/code/sshk-tools` 本身**，不是父目录、不是 `apps/desktop`、也不是多根工作区 | `.vscode/` 只在**工作区根**生效；开父目录时我们提交的配置根本不会被读取 |
| 2 | 安装并启用 **Vue - Official (Volar)**；若装了老 **Vetur** 必须禁用 | `.vue` 的类型检查由 Volar 提供 |
| 3 | `Ctrl+Shift+P` → **Developer: Reload Window**（重载窗口） | 新增 `tsconfig.json` / `.vscode` 后，TS Server 必须重启才会重新发现项目；只在编辑器里刷新文件无效 |
| 4 | `Ctrl+Shift+P` → **TypeScript: Select TypeScript Version** → 选 **Use Workspace Version** | 指向 `node_modules/typescript/lib`（TS 6.x），避免用 VS Code 内置版本 |
| 5 | `Ctrl+Shift+P` → **TypeScript: Restart TS Server** | 清掉旧的推断项目缓存 |
| 6 | 打开任一 `.vue`，`Ctrl+Shift+P` → **TypeScript: Go to Project Configuration** | 应跳到 `apps/desktop/tsconfig.json`；若跳到别处或提示 inferred project，说明第 1 步没做对 |
| 7 | 若仍有残留红线：`Ctrl+Shift+P` → **Developer: Show Logs...** → 选 **Vue Language Server / TypeScript** 看它实际用了哪个 tsconfig | 用于定位「IDE 选错项目」的最终证据 |

自查命令（CLI 与 IDE 对照，应在仓库根执行）：
```bash
pnpm exec tsc --noEmit -p tsconfig.base.json
pnpm exec tsc --noEmit -p tsconfig.json
pnpm exec tsc --noEmit -p apps/desktop/tsconfig.json
pnpm --filter @sshk/desktop build
```
三条 tsc 全 0 错误即代表代码侧无问题；此时仍红，100% 是第 1/3/4/5 步没生效。

| 快捷键 | 行为 |
|---|---|

## 九、后期路线图：运行时导入 / 安装 / 卸载工具包（#8，方案已定稿，实现排期）

> 2026-11-13 用户拍板：**A** 分级沙箱 / **B** 本轮只定契约 / **C** 三种信任机制叠加都做。
> 构建期发现（已实现）保证「放进 `tools/` 零改动」；运行时发现是**叠加能力**，不替代前者。

### 9.1 五点定稿

| # | 结论 |
|---|---|
| 包格式 | **开发态目录 + 分发态 `.sshktool`（zip）**，包内仍是同一份 `tool.manifest.json`；解压防 Zip Slip、限文件数/体积、拒符号链接 |
| 完整性 | L0 结构/schema 白名单 → L1 整包 SHA-256 TOFU 指纹 → L2 Ed25519 签名（官方内置公钥 + 用户导入公钥）。**哈希只证明「没被改过」，证明不了「不是恶意代码」**，任意代码执行由沙箱分级与安装时显式授权兜住 |
| 版本兼容 | `package.schemaVersion`（宿主 `TOOL_PACKAGE_SCHEMA_VERSION=1`）、`requiresHost.api`（宿主 `HOST_API_VERSION=1.0.0`）、`requiresHost.capabilities[]` 逐项对 `ToolHostCapabilities` 比对；不满足拒绝安装，能力缺失写进 `pluginStatus` 并在 UI 明示，不隐式降级 |
| 运行时沙箱 | `package.sandbox: main \| utility`、`package.ipcAllowlist[]`；外部默认 `utility`。本轮**只定字段不实现进程** |
| 生命周期 | 上传 → 结构/schema → 指纹/签名 → 能力协商 → 用户确认权限清单 → 解压 → 原子写 `installed.json` → 注入运行时 MANIFESTS → 加载 → 启用/禁用 → 卸载（摘 IPC、删目录、清孤儿配置）。任一步失败整体回滚 |

### 9.2 信任与加载决策矩阵（A）

| 签名 | 公钥 | 用户显式信任 | 加载位置 |
|---|---|---|---|
| 有效 | 官方内置 / 用户导入 | ✅ | `main`（与 builtin 同等） |
| 有效 | 用户导入 | ❌ | `utility` |
| 无签名 / 校验失败 | — | — | 一律 `utility`，安装弹窗标红 |

裁决纯函数 `canLoadInMain()` 落在 `packages/shared/src/trust.ts`，可单测，渲染层不得自行提权。

### 9.3 C：三重机制叠加

| 机制 | 落点 | 回答 |
|---|---|---|
| TOFU 指纹 | `installed.json` 的 `sha256` + 安装时间，升级必须重新确认 | 装完后有没有被换过 |
| 官方内置公钥 | `OFFICIAL_PUBLIC_KEYS`（Ed25519 PEM，支持多把轮换） | 是不是官方发的 |
| 用户导入公钥 | 设置中心「信任的发布者」，可导入/撤销 PEM | 第三方发布者我认不认 |

签名对象 = `manifest + 整包哈希`；哈希白名单是**本机 installed.json**，不是全局白名单。

### 9.4 B：本轮只定契约，不搭 utilityProcess 骨架

| 冲突点 | 现状 | 搭骨架要动 |
|---|---|---|
| 插件加载器 | 主进程内 `await loader()` + `ipcMain.handle` | 改 messagePort 代理，重写加载器与 `guardedIpcMain` |
| 宿主能力 | `host` 是 `config`/`repository`/`safeStorage` 直接对象引用 | 全改 IPC 代理，否则跨进程传不过去 |
| 调用方 | 无 `.sshktool` 安装入口、无 `installed.json` | 骨架无真实调用方，只能写无法端到端验证的死代码 |
| 门禁 | `check-preload` / `check-boundaries` 基于单出口主进程 | 需同步调整，牵动 verify |

本轮已落：`ToolDescriptor.package?: ToolPackageContract`、`trust.ts` 常量与类型、`check-package-contract.mjs` 门禁。builtin 工具不填 `package`，默认 `main`，行为不变。真正起进程与安装入口**同轮实现、一次成型**。

### 9.5 排期（#35，非本轮）

zip 解析与 Zip Slip 防护、TOFU 指纹、Ed25519 签名与公钥管理 UI、版本/能力协商、权限确认弹窗、`installed.json` 原子写入、运行时 MANIFESTS 注入、升级/回滚；同步重构插件加载器与 host 能力为 IPC 代理，接入 `utilityProcess` + IPC 白名单。
