## 一、协同总原则

| # | 原则 | 说明 |
|---|---|---|
| C1 | **架构层分离** | `upload-core` 是 **main 进程能力包**（持 provider 实例、密钥 safeStorage、IPC）；`code-editor` / `rich-text` 是**渲染层组件包**。二者**互不 import**，避免把 Node 侧依赖拖进渲染 bundle |
| C2 | **一个注入点** | 富文本图片上传是两条能力唯一的功能交汇处，收敛为**组件回调契约**（§二），由工具侧（EDM）在 T7 注入一次实现，其余各包保持纯净 |
| C3 | **公共基座先行** | 三个新包 + 依赖清单一次性建好（B0），之后 R26 / R27 才能真正并行、逐个推进，不互相等 |
| C4 | **EDM 单一改序** | EDM 是双方共同的迁移对象，固定「先纯替换组件、后注入上传」（B6→B7），禁止两方同时改同一文件 |
| C5 | **门禁前置** | 每个批次提交都过 cph 五步；`apps/desktop build` 是唯一能暴露 Monaco worker 导入 / native 依赖 external 问题的环节（历史 MISSING_EXPORT 只在 build 报） |

> C5 在实施期再次被验证：B7 首次接线时 `apps/desktop build` 暴露了 `cpu-features` 原生模块无法被 rolldown 静态解析的问题（见 §八）。

## 二、交汇接口契约（C2 的具体定义）

`packages/rich-text` 的 `RichTextEditor` 暴露纯回调，**不 import `@sshk/upload-core`**：

```ts
// packages/rich-text/src/types.ts
export interface RichTextUploadHook {
  /** 工具侧注入：入参为本地文件，返回可插入富文本的 URL */
  (file: File): Promise<string>
}
// 组件 props: onUploadImage?: RichTextUploadHook; imageRule?: RichTextImageRule
```

工具侧（EDM，T7）注入实现，内部经 `window.api.upload.single(...)` 走 Upload Service；密钥与 profile 解析全在 main 进程完成。

```ts
// R26 暴露的 IPC（main 进程）
upload:single  -> { url, key/remotePath }
upload:batch   -> UploadResult[]（带进度事件 upload:progress）
```

**收益**：两包零编译依赖 → 可真正并行开工；upload-core 可被任意工具/任意组件复用（不只富文本）；rich-text 在未接上传的工具里仍可用（回调不传即降级为普通富文本）。

## 七、每批次门禁校验点

- cph 五步（提交必跑）：`tsc -p tsconfig.base.json` → `vue-tsc -p tsconfig.vue.json` → `eslint .` → `pnpm -C apps/desktop build` → `vitest run`。
- 补充核查：`check:latest`、`check:structure`、`check:contract`（**`upload` configGroup 的路径类字段必须用 `dir`/`file`**）、`check:preload`、`check:boundaries`。
- B6 后已验：Monaco worker 在 electron-vite/rolldown 下可解析（F3）、共享两包被 EDM 与 badge-studio 同时 import 时构建仍通过。
- B7 后已验：密钥不进渲染层（`upload:secret:state` 只回布尔）、进度事件通道已注册、工具级 overrides 能覆盖全局 profile。
- **仍需用户实跑**：真实 FTP/SFTP/OSS 连接、进度 UI、wangEditor 全屏、Monaco 多 tab、打包后运行时，见《EDM待收尾与验证清单.md》。

## 八、实现期实测补充（与 B0 预期不同的结论）

| # | 实测 | 处理 |
|---|---|---|
| 1 | `pnpm-lock.yaml` 并非必须用户手动提交 | cph 门禁的 `verifyDepsBeforeRun` 自动同步 lockfile + 新工具 `node_modules` 链接；每批随 commit 落库，CI `--frozen-lockfile` 不会失败 |
| 2 | `ERR_PNPM_IGNORED_BUILDS` 只是第一层，`cpu-features` 在 **build 期**还会炸 | rolldown 静态解析 `cpu-features/lib/index.js` 的 `require('../build/Release/cpufeatures.node')`；在 `electron.vite.config.ts` 把包名 alias 到 `apps/desktop/src/main/stubs/cpu-features.cjs`（抛错函数），`ssh2` 的 try/catch 自动回退纯 JS 探测 |
| 3 | 第三方 Node 依赖不必 external | `externalizeDepsPlugin` 只 external `apps/desktop/package.json` 的 dependencies；`basic-ftp`/`ssh2`/`ali-oss` 声明在 `packages/upload-core`，会被内联打进 main bundle，配合 electron-builder 排除 `node_modules/**` 反而正确 |
| 4 | `check:contract` 存在一条历史违规 | EDM 旧 `upload.remoteDir: string`；随 `upload` configGroup 重写一并消除，当前 `check:contract` 通过 |
| 5 | 新工具目录 + 深层 `v-for`/`v-model` 会让 vue-tsc 丢作用域 | 配置页表单拆成 `RemoteProfileForm.vue` / `CloudProfileForm.vue` 子组件，容器统一用 `ref`；新增依赖的类型检查须在 build 同步链接之后重跑 |
| 6 | 用户否定 R28 初版方向 | 「就近自动全收」会带来引入过多、顺序不可控、公共目录里非全公用的粒度问题；改为**源码显式 `<link>` + 逻辑 URI + head 提前去重**，就近链仅作存量兼容回退。详见《CSS引用与共享样式规划.md》§五 |
