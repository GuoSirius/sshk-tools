## 一、协同总原则

| # | 原则 | 说明 |
|---|---|---|
| C1 | **架构层分离** | `upload-core` 是 **main 进程能力包**（持 provider 实例、密钥 safeStorage、IPC）；`code-editor` / `rich-text` 是**渲染层组件包**。二者**互不 import**，避免把 Node 侧依赖拖进渲染 bundle |
| C2 | **一个注入点** | 富文本图片上传是两条能力唯一的功能交汇处，收敛为**组件回调契约**（§二），由工具侧（EDM）在 T7 注入一次实现，其余各包保持纯净 |
| C3 | **公共基座先行** | 三个新包 + 依赖清单一次性建好（B0），之后 R26 / R27 才能真正并行、逐个推进，不互相等 |
| C4 | **EDM 单一改序** | EDM 是双方共同的迁移对象，固定「先纯替换组件、后注入上传」（B6→B7），禁止两方同时改同一文件 |
| C5 | **门禁前置** | 每个批次提交都过 cph 五步；`apps/desktop build` 是唯一能暴露 Monaco worker 导入 / native 依赖 external 问题的环节（历史 MISSING_EXPORT 只在 build 报） |

## 二、交汇接口契约（C2 的具体定义）

`packages/rich-text` 的 `RichTextEditor` 暴露纯回调，**不 import `@sshk/upload-core`**：

```ts
// packages/rich-text/src/types.ts
export interface RichTextUploadHook {
  /** 工具侧注入：入参为本地文件，返回可插入富文本的 URL */
  (file: File): Promise<string>
}
// 组件 props: onUploadImage?: RichTextUploadHook; uploadAccept?: string; uploadMaxSize?: number
```

工具侧（EDM，T7）注入实现，内部经 `api('upload:single')` 走 Upload Service；密钥与 profile 解析全在 main 进程完成。

```ts
// R26 暴露的 IPC（main 进程）
upload:single  -> { url, key/remotePath }
upload:batch   -> UploadResult[]（带进度事件）
```

**收益**：两包零编译依赖 → 可真正并行开工；upload-core 可被任意工具/任意组件复用（不只富文本）；rich-text 在未接上传的工具里仍可用（回调不传即降级为普通富文本）。

## 七、每批次门禁校验点

- cph 五步（提交必跑）：`tsc -p tsconfig.base.json` → `vue-tsc -p tsconfig.vue.json` → `eslint .` → `pnpm -C apps/desktop build` → `vitest run`。
- `pnpm verify` 相关：`check:latest`（依赖写法）、`check:structure`（`type: module` / 时间规范禁用 `toISOString(`）、`check:contract`（**`upload` configGroup 的路径类字段 `remotePath`/`prefix` 等必须用 `dir`/`file` 类型，不能裸 `string`**）、`check:external`。
- B6 后重点验：Monaco worker 在 electron-vite/rolldown 下能否解析（F3）、wangEditor 全屏（F2）、多 tab 唯一 model URI（F6）。
- B7 后重点验：密钥不进渲染层、`upload:single` 进度事件、工具级 overrides 覆盖全局 profile。
