## 〇、背景与目标

当前 `.sshktool` 的「安装/校验/信任/加载」链路已验证可用（`runtime-installer.ts` + `pkg-validate.ts` + `trust.ts` + 设置中心导入 UI）。
但「**从源码生产一个可分发包**」的作者工具链是断的：

1. 只有写死示例目录的 `scripts/pack-runtime-sample.mjs`，且示例 `dist/*.js` 是**手写提交**，没有真实构建流水线；
2. 内建工具的 manifest 字段集与外部示例 manifest **不一致**，开发者靠手改 JSON、靠猜字段；
3. 安装期缺「内建/外部 id 冲突去重」与「升降级提示」。

**总体目标**：让开发者用**同一套目录结构 + 同一套配置表单**完成开发，再一键选择「打进应用（内建）」或「导出 `.sshktool`（外部）」，其余交给工具链。

## 一、需求与疑问逐条梳理

> 你列的条目为 1 / 2 / 3 / 4 / 5 / 6 / 8（未含 7）。

### ① 打包脚本命名不规范（带 example 字样）
- 现状：`scripts/pack-runtime-sample.mjs` 写死 `examples/runtime-sample` 目录，名不副实。
- 结论：重命名为通用脚本（建议 `scripts/pack-tool.mjs`），参数化工具 id，移除 example 残留；`examples/` 下的示例包保留作端到端回归用例，但不再由"示例专用"脚本生成。

### ② 包配置项太多太杂，不能让开发者手填 / 猜测
- 现状：`package` 契约含 `schemaVersion / requiresHost.api / requiresHost.capabilities / sandbox / ipcAllowlist`，外加内建侧 `configGroups / defaults / dependsOn / visibility / requiredGrant` 等，开发者需查源码才知道能写啥。
- 结论（对应你之前提到的"开发模式与构建模式配置项/展示略不同"）：在**开发模式**下，对所有包（不区分内建/外部）提供一个**统一配置表单**：
  - `capabilities` → 复选，选项来自宿主 7 项能力（见 §四）；
  - `ipcAllowlist` → 复选，选项来自宿主 `IPC_CHANNELS` 全表（见 §四）；
  - `sandbox` → 单选（utility / main，main 强制要求签名）；
  - `schemaVersion` / `requiresHost.api` → 自动取宿主常量，不手填；
  - 其余包配置项（基础信息、menus、configGroups、defaults 等）→ 一并纳入表单。
  - 提交后**写回 `tool.manifest.json`**。用户再决定「打进应用」或「导出 `.sshktool`」。
- 入口：在现有「设置 → 工具与权限」列表每项加「配置」按钮，弹对话框/配置页（见 §三、§五）。

### ③ 开发与目录结构对内外建应完全无差异
- 结论：**作者视角零差异**——同一套 `tools/<id>/` 目录（含 `assets/ scripts/ src/ tool.manifest.json`），同一套能力声明。差异**只发生在打包这一步**：
  - 内建：保持 `.vue` + `src/main/index.ts`，由 `electron-vite` 直接编入应用；
  - 外部：构建步骤额外产出「零 import 渲染层 `dist/page.js` + 打包 `main.js`」，再打成 `.sshktool`。
- 即：源码结构 = 唯一真相；分发形态 = 构建参数决定。

### ④ 内建已分发、又打外部包导致重复安装
- 现状：`runtime-installer.installPackage` 只看 `installed.json`，不感知内建目录，可能出现「应用已内置 `edm-studio`，又导入同名 `.sshktool`」的双份。
- 结论：安装前做**跨源去重**——若待安装包 `id` 已存在于内建清单（宿主 builtin catalog），**拦截并提示**："该工具已内置于本应用（vX），重复安装会造成功能冲突；如需替换请先在工具与权限中禁用内建，或确认覆盖安装"。默认**拦截**，需用户二次确认才允许覆盖（决策点 D-C）。

### ⑤ 外部包重复导入的升级 / 降级提示
- 现状：`installPackage` 仅当哈希不同提示"已按升级覆盖安装"，**未区分升级/降级、且覆盖前未征求同意**（line 188-190）。
- 结论：引入版本比较（semver），分三态处理：
  - **升级**（新 > 已装）：提示"将从 v旧 升级到 v新"，确认后覆盖；
  - **降级**（新 < 已装）：**强警告**"正在降级，可能丢失新版本能力/数据"，默认**拒绝**，须显式 opt-in 才允许；
  - **同版本不同哈希**：提示"重装同版本（内容有改动）"，确认后覆盖。
- 决策点 D-D：降级默认拦截还是允许（建议默认拦截 + 显式放行）。

### ⑥ 补 `OFFICIAL_PUBLIC_KEYS`
- 现状：`trust.ts` 中 `OFFICIAL_PUBLIC_KEYS = []` 为空，所有外部包都只能是 `user-imported` 层级，每个接收方都得手动导入一次公钥。
- 结论：生成一把**官方 Ed25519 密钥对**：
  - 公钥 PEM（含 `keyId = sha256(pem)`、`since` 日期）登记进 `OFFICIAL_PUBLIC_KEYS`；
  - 私钥**不放仓库**（放 gitignored `secrets/` 或发布流水线环境变量），仅签名时本地使用；
  - 配套新增 `scripts/sign-tool.mjs`：对 `manifest 原文 + 排序后的 name:sha256 清单` 签名，产出 `SIGNATURE` 文件 + 回写 `package.signature`；
  - 官方签名的包安装时自动 `official` 层级，**无需接收方导入公钥**。
- 决策点 D-E：官方私钥存放与"谁/何时执行签名"（发布流水线 vs 本地一次性）。

> **落地更新（2026-11-14）**：公钥不再内联在 `trust.ts`，改为独立数据文件
> `packages/shared/src/official-keys.json`（多把并存，追加/吊销只改数据）；`trust.ts` 导入后导出
> `OFFICIAL_PUBLIC_KEYS`，`check:signature` 与 `keys:init` 直接 `JSON.parse` 该文件，不再正则解析 TS 模板字符串。
> 私钥改放用户级 `~/.sshk/official-signing-key.pem`（或 env / CI Secret），由 `pnpm keys:init` 生成/导入，
> 换设备推荐各持一把私钥 + 公钥并存，详见 `docs/05-release/官方签名密钥跨设备开发.md`。

### ⑧ 外部包目录结构是否同内建（assets/scripts/src + manifest）
- 结论：**作者目录结构完全一致**（见 §三）。`.sshktool` 作为分发产物，内部打包内容与内建一致；差异仅在于外部包运行时加载的是**构建产物**（`dist/page.js` / `dist/main.js`）而非原始 `.vue`/`src`。
- 决策点 D-F：`.sshktool` 内**是否携带源码 `src/`**：
  - 方案 A 仅 dist+manifest+assets（体积小、源码保密，但难二次调试）；
  - 方案 B 全量携带（便于审计/二次开发，体积大）。
  - 建议外部分发默认 A，内部/开源场景可选 B。

## 二、统一架构原则

```
               ┌──────────────── 作者态（唯一真相）────────────────┐
               │  tools/<id>/                                     │
               │   ├─ tool.manifest.json   (统一字段，见 §三)       │
               │   ├─ assets/  scripts/  src/(含 .vue + main)       │
               │   └─ （开发模式配置表单写回 manifest）            │
               └───────────────────────┬──────────────────────────┘
                                        │ 打包目标选择
                    ┌───────────────────┴────────────────────┐
            内建（打进应用）                          外部（导出 .sshktool）
       electron-vite 直接编 .vue              构建零import dist + 打包 main
            │                                        │
            ▼                                        ▼
   宿主 builtin catalog                         zipSync → <id>.sshktool
   （随应用发版，无需签名）                （可选 sign-tool 签名 → official）
                                           接收方：设置中心导入 → 校验/去重/升降级
```

**铁律**：开发模式、目录结构、工具能力声明，内建与外部**完全一致**；唯一变量是「分发形态」。

## 三、工具包标准目录结构与 manifest 规范（统一字段）

目录（作者态，内建/外部同构）：
```
tools/<id>/
├── tool.manifest.json      # 唯一事实源；id 必须 = 目录名
├── assets/                 # icon.svg、静态资源（icon:"auto" 时启用）
├── scripts/                # 工具自有脚本（可选）
├── src/
│   ├── main/index.ts       # 默认导出 (deps)=>void 注册函数（内建入口）
│   └── renderer/*Page.vue  # 渲染页（内建入口）
└── dist/                   # 仅外部分发构建产出：page.js（零import）/ main.js（打包）
```

manifest 统一字段表（开发模式表单覆盖全部）：

| 分组 | 字段 | 来源/选项 | 表单控件 |
|---|---|---|---|
| 基础 | id / name / description / category / tags / icon / entryRoute / enabled / visibility | 文本/选择 | 输入+下拉 |
| 菜单 | menus[] | — | 列表增删 |
| 插件 | plugin.source | builtin / external | 单选（打包时定） |
| 插件 | plugin.main / plugin.renderer | 路径（内建=.vue/.ts；外部=dist） | 输入（构建自动写） |
| 插件 | plugin.channels | 工具自身通道 `<id>:<name>` | 自动派生+可编辑 |
| 契约 | package.schemaVersion | 自动取 `TOOL_PACKAGE_SCHEMA_VERSION`(=1) | 只读 |
| 契约 | requiresHost.api | 自动取 `HOST_API_VERSION`(^1.0) | 只读 |
| 契约 | requiresHost.capabilities | **7 项宿主能力复选** | 复选框 |
| 契约 | sandbox | utility / main | 单选（main→需签名） |
| 契约 | ipcAllowlist | **宿主 IPC_CHANNELS 全表复选** | 复选框 |
| 契约 | signature | 签名对象（sign-tool 写） | 自动 |
| 配置UI | configLayout / configGroups / defaults | 同内建现有结构 | 高级编辑（JSON 或子表单）|
| 依赖 | dependsOn / configDeps / requiredGrant | 同内建现有结构 | 输入/选择 |

> 说明：`capabilities` 7 项 = `getToolSecret, setToolSecret, chat, listProviders, chatByProvider, listModelsByProvider, runLocalOcr`。
> `ipcAllowlist` 可选集 = `IPC_CHANNELS` 全部键（host 通道），**与 `plugin.channels`（工具自身通道）是两回事**，表单中分两个控件。

## 四、开发模式配置表单（UI 方案）

- **入口**：「设置 → 工具与权限」列表中，每项加「配置」按钮（复用现有 `SettingsPage.vue` + 已有的 `tools:*` 通道族）。
- **形态**：弹窗对话框（或右侧抽屉），分「基础 / 菜单 / 插件 / 契约 / 高级配置」标签页。
- **数据回写**：表单提交 → 合并写回 `tools/<id>/tool.manifest.json`，并触发 `pnpm verify`（契约门禁）即时反馈。
- **开发者模式开关**（决策点 D-A）：是否仅"开发者模式"下显示「配置」「打包」按钮？建议加 `app.developerMode` 开关，避免普通用户误改。
- **打包触发**（决策点 D-G）：表单页提供「打包应用（内建）」与「导出 .sshktool」两个动作，后者调用 `scripts/pack-tool.mjs <id>`。

## 五、构建与打包流水线（补齐缺口）

| 环节 | 现状 | 目标产物 | 新建/改造 |

| 运行时 bundle 构建（3a） | 示例 `dist/*.js` 手写提交 | 从 `src/` 产出零 import `dist/page.js` + 打包 `dist/main.js` | 新增构建配置（external 专用，Vue 外置为 `window.SSHK`，main 打包单文件）|

## 六、安装期防护（④⑤）

在 `runtime-installer.installPackage` 前插入两道闸（纯函数，可单测）：

1. **跨源去重（④）**：合并「内建 catalog id 集合 ∪ 已安装 id 集合」。若命中内建 → 拦截 + 提示（D-C 决定默认拦截/覆盖确认）。
2. **升降级裁决（⑤）**：比对 `pkg.version` 与 `installed.json` 中已装版本：
   - 新 > 旧 → 升级提示 + 确认覆盖；
   - 新 < 旧 → 降级强警告 + 默认拒绝，显式 opt-in 才允许；
   - 同版本异哈希 → 重装提示 + 确认。
   全部在**写盘前**征求同意，不再"先覆盖后提示"。

## 七、官方签名（⑥）

- 生成 Ed25519 密钥对（一次性）；公钥登记进 `OFFICIAL_PUBLIC_KEYS`，私钥 gitignored。
- `sign-tool.mjs` 签名对象 = `manifest 原文 + '\n' + 排序 name:sha256 清单`（排除 `SIGNATURE`）。
- 安装时 `verifySignature` 命中官方公钥即 `official` 层级，免接收方导入。
- 决策点 D-E：私钥托管与签名触发时机。

### 9.1 决策之外，本轮补齐的分发链路规范（已修复 5 处缺陷）

| 项 | 结论 | 落地 |
|---|---|---|
| **规范签名对象** | `canonical manifest`（剔除 `package.signature`）+ 其余文件（排除 manifest 自身与 `SIGNATURE`）的 `name:sha256` 排序清单。**禁止把签名值自身或 manifest 自身哈希算进去** —— 否则构成循环依赖，验签必失败 | `trust.ts` 头部为唯一裁决方；签名侧 `scripts/lib/tool-package.mjs::buildSignaturePayload`，验签侧 `runtime-installer.ts::verifySignature`，两侧由 `check:signature` 闭环校验 |
| **公钥独立数据文件** | 多把公钥并存时，公钥是数据不是代码：单独 `official-keys.json` 维护，`trust.ts` 只导入导出，追加/吊销不改逻辑 | `packages/shared/src/official-keys.json`；`check-signature.mjs` / `init-signing-key.mjs` 直接读 JSON；`trust.test.ts` 校验 keyId 与 pem 匹配 |
| **源目录裁决** | 打包/签名只针对外部分发包：`--src` 显式优先；否则优先 `examples/<id>` 再 `tools/<id>`，同名时打印提示（曾误签同名内置 `tools/template-tool` 导致产物缺 `dist/`） | `scripts/lib/tool-package.mjs::resolveToolSrc` |

## 十、已知限制 / 风险

- **T3 构建是最大不确定项，且仍未开工**：当前示例的 `dist/page.js` / `dist/main.js` 是**手写**零 import 产物，尚无 external 专用构建配置；`window.SSHK` 已扩展为全量 Vue API 桥，但若实际构建出现缺口仍需扩展宿主侧 `main.ts`。
- **跨源去重依赖内建 catalog 可见性**：需确认运行时能拿到完整 builtin id 集合（宿主 `loadToolPlugins` 已有 builtin 清单，可复用）。
- **官方私钥一旦泄露**影响全量信任：私钥只存本机用户级 `~/.sshk/official-signing-key.pem`、env 或 CI Secret，绝不入库；换设备不搬私钥而是各持一把 + 公钥并存（`pnpm keys:init`，见 `docs/05-release/官方签名密钥跨设备开发.md`）；`check:signature` 门禁会验证产物签名与登记公钥匹配。
- **签名对象口径是跨进程契约**：签名脚本（Node）与验签（Electron 主进程）各自实现，任一侧漂移都会让签名包静默降级为 utility 沙箱。规范写在 `trust.ts`，由 `check:signature` + `runtime-installer.test.ts` 端到端用例双侧兜底。
- **仍未实现**：D-A 开发者模式开关、T4 配置表单、T5 打包动作 UI、T3 external 构建配置（见 §九 / §八）。
