## 二、njk 数据注入：分层作用域上下文

### 2.1 现状差距

| 维度 | 现状 | 目标 |
|---|---|---|
| 表单数据 | `mail.data` 平铺 + `slot_*` 注入（`render.ts:38-41`） | 保留兼容，另加作用域元数据 |
| 元数据 | meta.yaml 只用于树/播种/校验/UI，**完全不进渲染上下文** | 模板/片段各自注入自己的四级 meta |
| favicon | 六级 meta 有 `favicon`、UI 有继承链；模板 `<link rel="shortcut icon" href="favicon.ico">` 写死，仓库无该文件、无代码替换 | 模板写 `{{ meta.favicon }}` 由元数据渲染 |
| 作用域 | 模板级/片段级 data 已有回落与品牌硬校验 | meta 同样按作用域隔离；片段**额外可选**看到模板 ctx（用于按模板做样式区分） |
| slot 通道 | `slot_<key>` = 已渲染 HTML 字符串塞进 ctx（`render.ts:40`） | **敲定方案 A**（§2.4，修订 8/13）：ctx 允许含 slot HTML 字符串，不追「只存数据」；片段看模板 ctx 用 `template.*` 命名空间注入（§2.2） |

### 2.2 上下文结构（含修订 1 / 修订 13）

```text
模板渲染 ctx:
  <data 字段平铺>          subject/preheader…（兼容现有裸变量，存量 njk 零改动）
  meta.brand   { code, name, favicon }
  meta.type    { code, name, favicon }
  meta.family  { code, name, favicon, slots }
  meta.version { code, version, name, favicon }

片段渲染 ctx（挂在模板下组装/预览时）:
  meta.<四级>                ★ 片段自己的四级元数据（主体，平铺）
  <placement.data 平铺>      ★ 片段自己的数据（主体，平铺）
  template                  ★ 可选：模板 ctx 整体挂在该命名空间下
                               template.<data 字段>      模板 data（subject/preheader…）
                               template.meta.<四级>      模板四级 meta（brand/type/family/version）
  // 命名空间隔离：template 与片段自身字段不在同一层，不合并、不覆盖同名（修订 13）
  // 片段用 {% if template %}…{% endif %} 守卫；未选模板（片段独立开发/预览）时 template 为空对象，照常渲染

片段独立渲染 ctx（片段开发 / 未选模板预览）:
  meta.<四级> + <片段自身 data>，template 为空对象，无模板 ctx 也能跑
```

| 决策点 | 结论 | 理由 |
|---|---|---|
| meta 命名 | 统一 `meta.*` 命名空间，**不与 data 平铺混用** | `fields`/`sample`/`version` 等裸名易与 data 撞车；保留 data 平铺是为存量 njk 零改动 |
| 片段可见模板 ctx | **存在才注入，不强制**；模板 ctx 整体挂 `template.*`，**不与片段自身字段平铺合并、不覆盖同名**（修订 13） | 满足「片段按不同模板做样式区分」；未选模板（片段开发）时优雅降级；分层隔离使同名字段天然无冲突，Q7 优先级规则自然消解 |
| favicon 模板写法 | `{% if meta.favicon %}<link rel="shortcut icon" href="{{ meta.favicon }}" />{% endif %}` | 空值不出空 link；`.ico` 已在 `IMAGE_EXTS` 白名单，无需新字段 |
| ctx 内容 | **敲定方案 A：允许含 slot HTML 字符串**，不追「只存数据」（§2.4） | 源码级展开风险/改动均大且无业务收益；slot HTML 是 nunjucks 声明式注入的标准用法 |
| meta 来源链路 | 渲染 IPC 按 templateVersionId / fragmentVersionId 反查内存内容树取四级 meta，随 compose 入参传入 | 不依赖「只有 html 字符串」的 render 入参；ID 在邮件绑定与预览 selector 中均可拿到 |

> **片段内按模板区分样式的写法示例**：
> `{% if template and template.meta %}{% if template.meta.family.code == 'standard' %}…专属样式…{% endif %}{% endif %}`
> 模板 data 也可用 `{{ template.subject }}` 读取；因整体挂在 `template.*` 下，不会与片段自身的 `subject` 等字段相撞。

### 2.4 slot 注入方案敲定：方案 A + 模板 ctx 命名空间注入（修订 8 / 13）

**背景**：v0.2 曾计划把 slot 改为「源码级展开」以满足「ctx 只存数据」。用户 12:08 追问风险与改动量，复核后改判保留现状（修订 8）；用户 12:44 再次确认——**敲定方案 A**，并把「片段看模板 ctx」从平铺 merge 修正为命名空间注入、不合并覆盖（修订 13）。

#### 两机制对比（通俗版）

以「做三明治」类比：

| | 方案 A（现状·渲染后注入·**已敲定**） | 方案 B（源码级展开·已放弃） |
|---|---|---|
| 做法 | ① 每片配料（片段）先单独做好：片段 njk + 片段 data → 一段 HTML<br>② 把 HTML 当字符串塞进 `slot_*` 变量<br>③ 渲染模板，`{{ slot_x \| safe }}` 原样放入 | ① 不先做配料，把片段 njk 源码直接拼进模板<br>② 整份一次渲染<br>③ 每段配料包 macro + 现场 `set` 字段 |
| 本质 | 两次渲染，片段与模板各渲各的 | 一次渲染，片段源码即模板一部分 |
| 现状落点 | `compose.ts:58` → `render.ts:40` | — |

#### 风险与改动量评估（方案 B 放弃依据，存档）

| 点 | 方案 B 实情 | 方案 A |
|---|---|---|
| `{% set %}` 作用域 | 宏内局部、顶层/for 块影响后续；多片段同层 set 同名字段互相覆盖，必须逐片段包 macro 隔离，嵌套深易踩坑 | 不涉及 |
| fields 自动生成 set | 字段动态，需写「数据→njk 代码」生成器（字段名合法性/对象/数组/HTML 值/autoescape 配合） | 不涉及 |
| richtext `\| safe` 回流 | 片段源码并入主模板后 autoescape 全局统一，#187/#188 刚固化的 safe 纪律被重新考验 | 片段独立渲染，转义语义不变 |
| **片段间 data 隔离（致命）** | 一次渲染 = 单一共享 ctx，各片段自有 data；同名字段跨片段冲突，需专门解决 | 两次渲染天然隔离 |
| 改动量 | 新增展开器+生成器、改 render/compose 双链路、重写全部测试 | 小（ctx 加一个命名空间字段） |

#### 结论

- **保留方案 A**：ctx 允许含 `slot_*` HTML 字符串（nunjucks 声明式变量注入的标准用法，非缺陷）。
- **修订 1 + 修订 13（片段看模板 ctx）用命名空间注入实现，不合并覆盖**：

```ts
const fragCtx = {
  ...(p.data ?? {}),           // 片段自身数据仍平铺（存量 njk 零改动）
  meta: fragmentMeta,          // 片段自身四级 meta（平铺）
  template: templateCtx ?? {}, // 模板 ctx 整体挂 template.*：含模板 data + 模板 meta；无模板则 {}
}
const html = renderFragment(p.html, fragCtx)
```

- 片段内 `{% if template %}` 守卫后按模板信息做样式区分；未选模板时 `template` 为空对象，片段独立渲染照常。
- 两层字段不在同一命名空间，**不存在同名字段覆盖问题**，Q7 的「片段优先」优先级规则不再需要（自然消解）。
- **extends 解耦**：模板文件间继承靠 loader 解析 `@system/...`（§三），与 slot 注入是两件事，独立实现，不受本改判影响。
- 存量 56 个 njk 仍零改动（Q1）。

## 三、njk 跨文件继承：extends / include / import（需求 2）

### 3.1 结论与推荐写法

`{% extends '@system/elabscience/template/standard/default/template.njk' %}` **当前跑不通**（无 loader、`renderString` 读字符串、`@system` 只是 CSS link 的逻辑 URI）。推荐**复用同一套 `@system / @custom / @root` 前缀语义**新建模板 loader，让用户心智一致：

| 前缀 | 模板 loader 解析根 | 与现有 CSS URI 的关系 |
|---|---|---|
| `@system/…` | 系统资产根 `assets/edm/` | 同前缀、同根，语义一致；**独立实现，不与 CSS 解析函数混用** |
| `@custom/…` | 用户自定义资产根 | 同上 |
| `@root/…` | 当前来源根（系统/自定义自动判断） | 同上 |
| `./…` | 当前版本目录 | 同上 |

### 3.2 路径安全口径（修订 3）

| 项 | 方案 |
|---|---|
| `..` 处理 | **不禁用** `..`；允许写 `@system/a/../b.css` 这类相对上溯。解析后做 normalize，**兜底限定在根内**：最终路径越出允许根则拒绝（抛 `AppError('validation')` 或按现有错误处理），不因出现 `..` 字面就 throw |
| 其它禁止项 | 绝对路径、外链（`https?:`/`data:`/`file:`）仍禁止 |
| **CSS 同步改** | `core/css-refs.ts:69-70` 现在 `if (h.includes('..')) throw` → 改为「解析 + 根内兜底校验」；补测试覆盖「合法上溯不越界」与「越界拒绝」 |
| **文档同步项（已排查）** | `plans/14-EDM旧资产迁移.md:180` 现写「相对版本目录，禁止 `..`」→ 批次 B 同步改为「允许 `..`，兜底限根内」；历史台账 #177 条内「禁 .. 与外链」表述一并加批注指向本次修订（按规范历史条目不改写正文） |
| 渲染入口 | 有 `sourcePath` 的模板用 `env.render(name, ctx)` 走 loader；DB 里的字符串源码注册到内存 loader（临时名） |
| 与 slot 注入共存 | extends 母版 + 子模板 `block` 覆盖照常；模板经 loader 解析后按方案 A 注入 `slot_*` HTML 字符串；`autoescape:true` 与 `\| safe` 纪律沿用台账 #187/#188 |
