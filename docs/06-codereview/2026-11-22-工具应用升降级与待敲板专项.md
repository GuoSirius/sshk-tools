## 第一部分：工具⇄应用升降级专项（用户第 10 条）

### 1. 背景与问题

项目经历 D53「应用管理架构」重构：三个基础能力工具（file-manager / model-console / share-manager）已并入应用本体（`pages/app-admin/{files,models,share}` + `main/modules/{file,llm,share}`），纯工具仅剩 edm-studio / badge-studio / template-tool。用户要求本轮特别分析：哪些能力应在应用层、哪些该在工具层，是否还有"工具该升为应用 / 应用该降为工具"的错配。

### 2. 现状（复核已回源码确认，全部属实）

| 事实 | 证据 |
|---|---|
| 纯工具目录仅 3 个 | `tools/` → badge-studio / edm-studio / template-tool |
| 三能力页面在应用本体 | `apps/.../pages/app-admin/{files,models,share}/` 均存在 |
| 三能力 main 模块在应用 | `apps/.../main/modules/{file,llm,share}/` 均存在 |
| D53 边界已入规范 | `00-CONVENTIONS.md:72`：三模块属应用本体，依赖方向唯一=工具→应用，应用绝不 import 工具 |
| 依赖方向实际单向 | 全 `apps/` 扫描 `@sshk/(edm\|badge\|template)` 与 tools 相对导入 → **0 命中** |

### 3. 原因与定性

- **没有"应用该降级为工具"的能力本体**：三能力的管理页面与 main 模块都已落在应用本体，工具目录无残留。报告 §四结论"没有应用层该降到工具层的能力本体"经复核属实。
- **建议降级的仅 1 项 UI 组件**：「上传进度 toast」（工具内 → ui-kit）。复核确认这是**横向提取**（多消费者复用），不是能力降级，不改变归属。
- **建议上提的 4 项都是跨工具重复的纯函数/胶水**：模型剥壳（J-03）、配置预设（J-06）、share:resolve（J-05）、readAsDataUrl（J-02），符合 §1.3"≥2 消费者复用→packages"判据——属"工具层胶水→共享层"的归位，不是工具升应用。

### 4. 根因（复核新发现，报告未点透）

D53 的"应用不 import 工具"依赖方向目前**成立但只靠文档约束**（`00-CONVENTIONS.md:72` 纯文字），无 lint/门禁规则兜底；工具侧胶水（产物路径解析 / 输出剥壳 / 进度展示 / readAsDataUrl）确实分散在多个工具与包中（J-02/03/04/05/08）。这与 J-09「胶水层边界规范缺失」是同一根因：**边界划了，但归位规范与机械约束没跟上**。

### 5. 所有建议方案（待敲板）

| 方案 | 内容 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. 维持 D53 归属 + 补胶水归位规范（推荐）** | 三能力归属不动；在 §1.3 补"工具侧胶水归位规范"（产物路径解析/输出剥壳/进度展示/文件读取 4 类）；对应重复实现按 §1.3 上提 | 尊重已落地架构、改动聚焦、消除重复 | 需同步补规范文档；部分胶水提取涉及跨包改动 |
| B. 维持归属 + 仅文档说明（报告 C 方案） | 归属不动，§1.3 明确"产物路径解析=工具责任"，不上提胶水 | 改动最小 | 重复胶水继续存在，未来新增工具仍会各写一份 |
| C. 进一步上收三能力工具侧胶水到应用宿主 | 连 share:resolve 等都收进应用，工具只声明规则 | 工具更薄、边界更硬 | 增大应用宿主，D53"应用不强依赖工具"被弱化；工作量大 |

**主审建议：方案 A**。理由：三能力归属无需变动（已正确）；真正的问题是胶水重复与边界无机械约束，用"补规范 + 按 §1.3 上提"一次性解决，既符合用户第 11 条"可复用的留应用层、该建包的建包"，又不动摇 D53。
