## 一、H3 全局错误边界 + 日志落盘（P1，本目录地基——先做）

### 背景
当前用户报障只能靠「截图 + 主进程终端输出」；渲染层异常无捕获，主进程堆栈只在开发终端可见。

### 方案

| 层 | 设计 |
|---|---|
| 日志核心 | `apps/desktop/src/main/logger.ts`：分级（debug/info/warn/error）+ 按天滚动文件（`userData/logs/sshk-YYYY-MM-DD.log`，保留 7 天自动清理）+ IPC 事件 `log:frontend` 接收渲染层日志 |
| 渲染层 | ① Vue `app.config.errorHandler` 全局捕获（含组件栈）；② `window.onerror` / `unhandledrejection`；③ `console.error` 镜像转发 main 落盘；④ 统一封装 `logFront(level, msg, detail)` 供工具/组件主动上报 |
| 主进程 | `unhandledRejection` / `uncaughtException` 捕获落盘；IPC 意外异常（03 的 handleOk unknown 分支）落盘；electron-updater、模型网关、上传 Service 的关键节点打 info |
| 设置入口 | 设置抽屉「系统与数据」加：打开日志目录按钮 + 当前日志文件大小 + 「清空日志」 |
| 脱敏红线 | 日志**绝不写入**：apiKey、上传密码、访问密钥、口令（safeStorage 相关只记布尔与 profileId） |

## 四、U2 验证引导内置应用（P1，用户点名「做完美、不要鸡肋」）

### 设计原则（防鸡肋的关键决策）
1. **不是静态清单搬运**——不是把 A-E 表格塞进页面让人照着读；而是**可执行的检查步骤**：每条 = 操作引导（一句话+入口直达按钮）+ 判定（自动检测的自动判，需人工看的勾选确认）。
2. **与遗留总账同源**——步骤清单数据化存在 `docs` 之外（shared 常量或 JSON），验收清单文档与页内引导共用同一份数据源，避免两处维护。
3. **dev-only + developerMode 双入口**：dev 恒显示；打包版 developerMode 开启后显示（贴合"开发者自检"定位）。
4. **结果留痕**：每步可标「通过/未通过/跳过」+ 备注，结果存本地 JSON（`userData/verify-sessions/<日期>.json`），支持导出 markdown 汇报；下次进入显示上次进度，未完成项置顶。
5. **自动判定优先**：能自动检测的不让用户肉眼判（例：A1 横幅检测=查询宿主能力探测结果；E1 门禁=读取最近 verify 结果文件；B2 全屏 class 检查=注入检测脚本到 iframe/容器）。自动判不了的才人工勾选。

### 页面结构
```
验证引导页（dev/developerMode 可见，入口：更多下拉 + 设置抽屉）
├── 顶部：会话进度条（x/y 完成）+ 上次会话时间 + 导出报告按钮
├── 分组（对齐总账 A~F 六方向）：每方向折叠面板
│    └── 每条步骤卡片：
│         标题 + 一句话操作引导 + [直达入口] 按钮（如"打开上传配置工具"直接切路由）
│         自动判定区（可自动的）：实时检测结果 chip（✓/✗/无法自动）
│         人工确认区：通过 / 未通过 / 跳过 + 备注输入 + 截图路径粘贴（可选）
└── 底部：导出 markdown 报告（汇总通过率 + 未通过清单，直接可贴到对话里）
```

### 数据结构
```ts
interface VerifyStep {
  id: string                 // 对齐总账编号（A-V1、E-V6…）
  group: 'A'|'B'|'C'|'D'|'E'|'F'
  title: string
  guide: string              // 一句话操作引导
  entry?: { type: 'route'|'tool', target: string }   // 直达入口
  auto?: { kind: 'hostCapability'|'fileExists'|'catalogState'|'logScan', spec: unknown }  // 自动判定
  requiresPackaged?: boolean // 仅打包版可验（如口令双闸 C1-C3）
  relates: string[]          // 关联文档/规划编号
}
```

## 五、D-V3 流式打字核查（P1 小项）

### 已核实结论
全链路代码是真流式：`gateway.chat`（SSE 逐行解析→onDelta 逐片回调）→ main（每片即时 `webContents.send(llmChat, {delta})`）→ ModelConsolePage（onDelta 逐片 append）。**不存在缓冲到完成才渲染的逻辑**。

### 「一下子输出」的可能原因与核查方案
| 假设 | 核查方式 | 处理 |
|---|---|---|
| ① Agnes 端点聚合大分片/响应快 | 临时埋点：main 侧记录每个 delta 的到达时间戳与长度，控制台打印 `chunk#n size=xx gap=xxms` | 若 gap 普遍 >500ms 但单 chunk 很大 → 端点侧聚合，属上游行为；可加「打字平滑」渲染（前端按 30-50ms 定速逐字释放积压内容，视觉恒定打字感） |
| ② 端点不支持 stream 直接整包返回 | 看响应 content-type 是否 text/event-stream、chunk 数是否=1 | gateway 增加检测：非 SSE 响应时明确降级为非流式并在 UI 标注「（非流式）」 |
| ③ 渲染层 markdown 全量重渲染导致视觉跳变 | 观察 DOM 更新频率 | 若确认，chat 气泡渲染加节流（100ms） |
