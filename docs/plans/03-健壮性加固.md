## 一、H1 统一 IPC 失败契约（P0）

### 背景
N11 已验证：`ipcMain.handle` 只要 reject，Electron 就往主进程终端刷 `Error occurred in handler for 'xxx'` 堆栈；预期内业务失败（校验不通过、连不上）不是异常。

### 方案

| 项 | 设计 |
|---|---|
| 结果类型 | `packages/shared` 新增 `IpcResult<T> = { ok: true; data: T } \| { ok: false; code: string; message: string }`（code 用于分类：`validation` / `io` / `timeout` / `upstream` / `unknown`） |
| 主进程封装 | `apps/desktop/src/main/ipc-wrap.ts::handleOk(channel, fn)` —— 统一 try/catch：预期内错误（新自定义 `AppError` 类）→ resolve `{ok:false}`；意外异常 → resolve `{ok:false, code:'unknown'}` + **写日志**（接 04 日志落盘）；**永不 reject** |
| 渲染端封装 | `@sshk/ui-kit` 的 `callHostApi` 升级：识别 `IpcResult`，`ok:false` 时按 code 给对应 UI 反馈（warning/error message），返回类型收窄 |
| 迁移策略 | ① 新 handler 一律 `handleOk`；② 存量 handler 分三批迁：upload/llm（已部分结构化）→ tools/catalog 族 → os/theme/update 族；③ `check:preload` 门禁加规则：新增裸 `ipcMain.handle` 检查（ESLint 自定义规则或结构检查脚本扫描） |
| 兼容 | preload 层做一次解包适配，工具层零改动（仍拿 data 或收到结构化错误对象） |

### 任务
| # | 任务 | 复杂度 |
|---|---|---|
| H1-1 | `IpcResult` 类型 + `AppError` + `handleOk` 封装 + 单测 | 中 |
| H1-2 | 渲染端 `callHostApi` 解包升级 + 6 单测更新 | 中 |
| H1-3 | 存量 handler 分批迁移（每批一个 commit + 全量 verify） | 中 |
| H1-4 | 门禁：禁止新增裸 `ipcMain.handle`（verify 脚本规则） | 低 |

## 二、H2 宿主能力零裸调（P0）

### 背景
preload 是窗口启动快照，HMR 出现「新按钮 + 旧宿主」→ 裸调新增 `window.api.x.y` 报 `is not a function`。`callHostApi()` 已兜底，但靠自觉。

### 方案
| 项 | 设计 |
|---|---|
| ESLint 规则 | `eslint.config.js` 新增 `no-restricted-syntax`（或自定义规则）：renderer 目录内禁止直接访问 `window.api.<ns>.<method>`，统一 `callHostApi(() => window.api...)` 包装（规则要放行 `callHostApi` 内部实现文件与 `env.d.ts` 类型声明） |
| 分层豁免 | `host-api.ts`（能力探测实现）与 preload 类型定义文件豁免；其余 renderer 源码全量拦截 |
| 存量治理 | 全仓扫描现存的裸调点，一次性包上 `callHostApi`（预计集中在 EDM / badge / upload-config 的 window.api 调用处） |

### 任务
| # | 任务 | 复杂度 |
|---|---|---|
| H2-1 | ESLint 规则 + 豁免白名单 | 中 |
| H2-2 | 存量裸调点全量包装 | 中 |
| H2-3 | 工具开发指南 §四 补「必须走 callHostApi」示例 | 低 |

## 六、依赖漏洞复查方法（E-T1 / A-T5，用户问"如何复查"）

| 步骤 | 命令 / 动作 | 说明 |
|---|---|---|
| 1 | `pnpm audit --registry=https://registry.npmjs.org` | npmmirror 无 audit 端点，必须显式指官方源（热更新文档已注明） |
| 2 | `pnpm audit --prod` 关注 direct | 先看直接依赖，再传递依赖；`high/critical` 必修 |
| 3 | GitHub Dependabot 面板 | 仓库 Security → Dependabot alerts，与本地 audit 交叉核对（N7 fast-xml-parser 即此类） |
| 4 | 修复方式 | 优先 `pnpm-workspace.yaml` 的 `overrides` 精确覆盖（沿用 fast-xml-parser 先例）；major 升级走「latest 升级 SOP」（07 文档）单独 commit |
| 5 | 固化 | ④ 的产出记录进台账；每次 `pnpm up --latest` 后必跑 audit（写入 07 的 SOP） |
| 6 | 频率 | 收尾阶段先跑一轮全量清零；之后跟随每次批量升级跑，不设定时 |
