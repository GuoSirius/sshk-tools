# plans/12 · 分享服务工具化与三大基础能力分层设计（讨论稿，待拍板）

> 2026-11-19 立项。**本文档为讨论稿——用户逐项审核确认、通知后才开工。**
> 背景：分享服务功能持续扩张（路由管理/访问日志/挂载目录/代理规则），应用设置 ShareTab 已达 530 行 6 卡片，设置页定位（应用级少量开关）无法承载。同时借这次拆分，对模型/分享/上传三个基础能力的「应用层 vs 工具层」分配做一次系统盘点。

---

## 一、现状盘点：三大基础能力的分层现状

| 能力 | 能力实现层 | 配置数据 | 配置 UI | 工作台 UI | 消费方 |
|---|---|---|---|---|---|
| **模型** | 应用层：主进程网关（`chat/chatByProvider/listProviders`，密钥注入） | 应用层 `app.llm.*`（唯一权威） | 工具层 model-console（Provider 页） | 工具层（对话调试） | badge-studio、edm-studio 等全部工具经 host capabilities 共用 |
| **上传/文件管理** | 应用层：`upload-core`（驱动/传输引擎）+ IPC `upload:*` | 按工具归属：`tools.file-manager.*` + 密钥 `app:tool:file-manager:*` | 工具层（通道配置页） | 工具层（文件系统页） | file-manager 自用；edm-studio 经 `api.upload.*` |
| **分享** | 应用层：`@sshk/share-core`（ShareHub 单例）+ IPC `shareHub:*` | 应用层 `app.shareHub.*`（mounts/proxies/allowIndex/端口/自启） | **应用层设置 ShareTab（6 卡片 530 行，过载）** | 无（路由管理只读列表挤在设置里） | file-manager ShareDialog（toolId 归属鉴权）；挂载/代理为纯服务能力 |

**关键事实**：
- 分享的能力与数据已在应用层（配置键、hub-state.json、IPC 全齐），**只是 UI 全部挤在应用设置里**——拆分是纯 UI 层工程，数据零迁移。
- 三能力目前实际都是「能力+数据在应用层」；差异在 **UI 归属**：模型最干净（UI 在工具），分享最重（UI 全在设置）。

## 二、分层判据（本档定版，后续新能力按此归位）

1. **消费面**：被 ≥2 个工具消费的能力/配置 → 应用层；单工具专属 → 工具层（将来出现第二消费方再提升，YAGNI）。
2. **密钥与安全**：密钥一律应用层（safeStorage/主进程注入），工具层零接触——既有铁律不变。
3. **唯一权威**：跨工具必须一致的数据（模型 Provider、分享路由归属）→ 应用层单一数据源；UI 只是视图，允许多处入口。
4. **UI 性质**：配置型/管理台型 UI → 工具层；应用级少量开关（自启、端口、允许索引）→ 应用设置。
5. **可禁用性**：拆到工具的 UI 必须保证「工具未安装时应用层入口仍可用」（本档用户要求）。

## 三、分层分析结论（只针对这三能力）

### 3.1 合理的部分（不动）

| 项 | 理由 |
|---|---|
| 模型整体分层 | 「数据应用层 + UI 工具层」标杆，三能力中最优；所有工具共用一份 Provider，密钥主进程注入 |
| 上传能力（upload-core / `upload:*` IPC / host.getUploadKey） | edm-studio 等经 host 能力消费，能力名与工具名解耦（2026-11-19 改名已验证此边界正确） |
| 分享内核与 IPC（share-core / `shareHub:*`） | 能力已在应用层，拆 UI 不需要动任何内核/通道/配置键 |

### 3.2 需要改进的部分

| 项 | 问题 | 处置 |
|---|---|---|
| 分享管理 UI 全在应用设置 | 设置页 530 行 6 卡片，路由管理/访问日志/挂载/代理都是「工作台型」UI，超出设置定位；随功能扩张会继续膨胀 | **拆出新工具「分享服务」**（§四），应用设置瘦身为两卡片 |
| 上传通道**密钥命名空间**按工具归属（2026-11-19 16:58 核实修订，推翻本表上一版「profile 按工具归属」的说法） | 经逐项核实：①通道 profile **数据早已在应用层**——`app.upload`（UploadGlobalConfig：local/remote/cloud profiles + validation，R26 设计「全局预设 + 工具覆盖」）；②消费方**早已不止 file-manager**——edm-studio 图片上传（host.upload single/batch/profiles/listImages）、template-tool 图片库（file-picker 桥接）、应用设置预设导出（getUploadKey）全部在消费这些通道；③真正挂在工具命名空间的只有**密钥**：`app:tool:file-manager:<profileId>`（SECRET_TOOL_ID 硬编码）。错位后果：全局通道的密钥记在某工具账下，工具改名要迁密钥（已发生 upload-config→upload-manager→file-manager 两跳）、未来禁用/卸载 file-manager 时密钥处置会牵连其它工具的上传能力 | **建议尽早提升**（用户 2026-11-19 拍板意向）：密钥段 `app:tool:file-manager:<pid>` → `app:upload:<pid>`（与 `ACCESS_KEY_SECRET_ID='app:accessKey'` 同风格的应用级密钥段）；读写点收敛在 upload.ts 与 main/index.ts host 投影两处，迁移链扩展 services.ts（upload-config/upload-manager/file-manager 三个旧段 → app:upload，幂等） |
| 分享路由归属鉴权（跨工具不可操作） | 新分享工具若只能管自己的路由，路由管理页就废了（存量路由全归 file-manager） | **定版：分享工具 = 服务管理台**，可查看/撤销/续期**任意工具**的路由（`shareHub.list` 去掉 toolId 过滤或传通配；revoke/renew 校验放宽为 share-manager 特权）；具体工具内（ShareDialog）仍只管自己的。见 §六 待拍板① |

## 四、分享服务工具化方案

### 4.1 新工具 `share-manager`（定名待拍板②）

| 项 | 内容 |
|---|---|
| manifest | id `share-manager`，name「分享服务」，icon auto，`entryRoute: 'routes'` |
| 菜单（2 个） | `routes` 路由管理（默认）/ `logs` 访问日志 |
| 工具配置（`configLayout: multi`，3 页） | `service` 服务配置（服务状态 + 基础设置）/ `mounts` 挂载管理 / `proxies` 代理管理 |
| 渲染结构 | badge-studio/upload 范式：顶层唯一 `ShareManagerPage.vue` 壳按 menu prop 分发，菜单页 `pages/RoutesPage.vue`、`pages/LogsPage.vue`；配置页按既有工具配置机制注入（3 个配置组件） |
| 代码来源 | 直接从 `ShareTab.vue` 抽卡片迁移（挂载/代理/路由/日志四段几乎原样搬），`service` 页 = 状态卡片 + 基础设置卡片 |

### 4.2 应用设置 ShareTab 瘦身

- 保留：**服务状态** 卡片、**基础设置** 卡片（端口/网卡地址/自启/允许目录索引）。
- 移除：挂载目录、代理规则、路由管理、访问日志四段 → 迁入工具。
- 「留两处可用」实现：两处 UI 读写**同一配置键**（`app.shareHub.*`）与**同一 IPC**（`shareHub:*`），天然一致、零同步成本；工具未安装时应用设置两卡片完整可用（用户要求④落此）。

### 4.3 数据与 IPC：零迁移

- 配置键、hub-state.json、share-core 内核、`shareHub:*` 通道全部不动；本次为纯 UI 层拆分（与 2026-11-19 工具改名那次的四处迁移完全不同量级）。
- 新增改动仅两处内核边缘：①`shareHub:list` 支持全量列表（不按 toolId 过滤）②`revoke/renew` 放开 share-manager 的跨工具特权（鉴权处加白名单）。

### 4.4 不做清单（边界）

- 不动 file-manager 内 ShareDialog（工具内分享链接创建/复用/二维码，保持 toolId 归属自己的路由）。
- 不做访问日志持久化（保持环形内存 500 条，候选 3.3）。
- 不动挂载/代理的保存即生效机制。
- 应用设置不新增任何分享入口跳转（两处入口并存，发现成本由用户承担；如需引导可后续加）。

## 五、验收口径（供确认后写 verify-steps）

1. 未安装/禁用 share-manager：应用设置·分享服务两卡片可用，服务启停正常。
2. 安装 share-manager：默认进「路由管理」，可看全量路由（含 file-manager 创建的）、可撤销/续期任意工具路由；「访问日志」实时刷新。
3. 工具配置三页：服务配置启停/保存生效；挂载管理与应用设置历史数据一致（同键读写）；代理管理同。
4. 应用设置与工具配置两处同时打开修改，后保存者生效、无互相覆盖提示（同键 last-write，与现状一致）。
5. file-manager ShareDialog 行为不变（创建的路由 toolId 仍归 file-manager）。
