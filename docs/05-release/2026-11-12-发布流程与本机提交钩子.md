## 二、本机提交钩子（已知坑，必须按这套走）

**问题**：本机工具进程里 husky 跑不起来，直接 commit 报 `/usr/bin/env: 'sh': No such file or directory`。原因是钩子进程的 PATH 取自系统环境变量，里面既没有 `Git\usr\bin` 也没有 `bash`；在工具进程里改 `$env:PATH` 无效。

**解法**：`.git/cph/`（未跟踪）放两份 `#!/bin/sh` 钩子，提交时指定 hooksPath：

```bash
git -c core.hooksPath=.git/cph commit -m "feat: ..."
```

| 约束 | 说明 |
|---|---|
| shebang | 必须 `#!/bin/sh`，**不能** `#!/usr/bin/env sh`（又要去 PATH 找 sh，踩同一个坑） |
| shell 内建 | 取目录用 `${0%/*}`，**不用 `dirname`**（外部命令） |
| 工具调用 | `node ./node_modules/<本地相对路径>/bin`，相对路径，不用 `/c/...`（MSYS 会错转成 `D:\c\...`） |
| 门禁等价 | `pre-commit` = typecheck + lint + test；`commit-msg` = commitlint；**绝不用 `--no-verify`** |
| 启用时机 | 依赖装好（`pnpm install` + husky 就位）之后。**M0 首次提交依赖尚未安装，不指定 hooksPath**，用 git 默认 sample 钩子（不执行任何门禁） |

> M0 首次提交属于「依赖就绪前」的一次性引导提交，不是跳过门禁：此时 husky 尚未 install、`.git/hooks` 里只有 sample，本来就没有门禁可跳。

## 三、Git 协作铁律（每次改动）

```bash
# 1. 复核暂存范围，绝不 git add -A 盲加
git status
git add <具体文件>

# 2. 提交（依赖就绪后加 hooksPath）
git -c core.hooksPath=.git/cph commit -m "<type>: <简述>"

# 3. 推送（固定写法，避免凭证弹窗）
cd <repo> && SHA=$(git rev-parse HEAD) && \
GIT_TERMINAL_PROMPT=0 git -c credential.helper= -c credential.helper=wincred \
  push origin "$SHA:refs/heads/main" 2>&1 | tail -10; echo "EXIT=$?"
```

- 小步增量提交：每完成一个逻辑小节就单独 commit，不积攒。
- **绝不还原用户改过的文件**：提交时连同用户改动一并提交；禁止静默 `git checkout --` / `git restore` 丢弃。
- 不自动发布，本机不打 publish。

## 四、依赖与 lockfile（D20）

| 项 | 约定 |
|---|---|
| 版本字面量 | 所有外部依赖在 `package.json` 写 `"latest"`（如 `"dayjs": "latest"`） |
| lockfile | **`pnpm-lock.yaml` 必须提交**，`.gitignore` 里绝不忽略 |
| 安装 | **由用户在本机执行 `pnpm install`**，AI 不代跑（不写 node_modules / 不改 lockfile） |
| CI | `pnpm install --frozen-lockfile`；缺 lockfile 直接报错提示 |
| 升级 | `pnpm up --latest` 刷新 lockfile → 单独 commit → `pnpm verify` 全绿才合 |
| 巡检 | `node scripts/check-latest.mjs` 检查所有依赖是否仍是 `latest` / `workspace:*` |

## 七、`latest` 策略踩到的真实坑（M0 实测，2026-11-12）

依赖全取 latest 后，`pnpm verify` 第一次跑出两个 breaking change，已一次性修复：

| 现象 | 根因 | 处理 |
|---|---|---|
| `TS5102: Option 'baseUrl' has been removed` / `TS5090: Non-relative paths are not allowed` | `typescript: latest` 解析到 **TS 7.0.2**，移除了 `baseUrl`，`paths` 的值必须带 `./` | `tsconfig.base.json` 删 `baseUrl`，`paths` 改为 `["./packages/shared/src/index.ts"]` |
| `typescript-eslint does not support TS 7.0`（ESLint 10 + parser 8） | `@typescript-eslint/parser@8` 尚未支持 TS >=7，生态滞后于 TS latest | **用户决策（21:45 / D24）：TypeScript 改用 6.x 最新版**（npmmirror 查得 `6.0.3`），其余包仍 `latest`。两处 `package.json` 写 `"typescript": "6"`（受控例外，`check-latest.mjs` 白名单放行）；`eslint.config.js` 按已装 TS 主版本动态决定：装到 6 后用 `@typescript-eslint/parser` 检查 `.ts`，若本机仍残留 TS 7 则自动跳过解析器，保证门禁不炸 |

**结论**：全 latest 必须有 `pnpm verify` 兜底；每次 `pnpm up --latest` 刷新 lockfile 后要单独 commit、单独跑门禁，不能和功能开发混在一起（juice-email-cli 的 `inquirer 13→14` 也是同类教训）。

**结果**：两处 `package.json` 改为 `"6"` 后，本机 pnpm 在执行 `pnpm verify` 时自动完成解析，`pnpm-lock.yaml` 已同步到 **typescript 6.0.3**（AI 未代跑 `pnpm install`）；lockfile 随仓库提交，CI `--frozen-lockfile` 可复现。`pnpm verify` 在 TS 6.0.3 下全绿，`@typescript-eslint/parser@8` 正常检查 `.ts`。
