# 官方签名密钥：跨设备开发指引

> 适用场景：换电脑 / 多人协作 / CI 发布时，如何签名 `.sshktool` 而不把私钥带进仓库。

## 一、先给结论

| 问题 | 答案 |
|---|---|
| 新设备 clone 后能直接开发吗？ | **能**。`examples/*.sshktool` 是已签名的成品并已入库，`pnpm verify` 只用 `official-keys.json` 里的公钥验签，不需要私钥。 |
| 什么时候才需要私钥？ | 只有**重新生成/修改分发包并签名**时需要（`sign-tool.mjs`）。日常写工具代码、跑测试、打包应用都不需要。 |
| 私钥放在哪？ | 本机用户级 `~/.sshk/official-signing-key.pem`（Windows 为 `C:\Users\<你>\.sshk\`），或环境变量 / CI Secret。**永不入库**。 |
| 公钥放在哪？ | `packages/shared/src/official-keys.json` —— 独立数据文件，多把并存；`trust.ts` 只做导入，门禁脚本直接读 JSON。 |
| 换设备要搬私钥吗？ | **推荐不搬**：每台设备各生成一把，把新公钥追加进 `official-keys.json` 即可。 |

## 二、三条路径对比

| 路径 | 做法 | 优点 | 适用 |
|---|---|---|---|
| **A（推荐）每台设备独立密钥** | 新设备跑 `pnpm keys:init` → 打印可直接粘贴的 JSON 条目 → 追加进 `official-keys.json` 并提交 | 私钥永不传输、泄露面最小、可单独吊销 | 个人多设备、团队协作 |
| **B 复用同一把私钥** | 从公司密钥库/密码管理器取出 PEM → `pnpm keys:init -- --import <file>` | 公钥不变，无需改数据文件 | 必须保持单一签发方时 |
| **C CI Secret 签名** | 在 CI 环境变量注入 `SSHK_OFFICIAL_SIGNING_KEY` | 无人持有本机私钥、发布可复现 | 正式发布流水线 |

> 公钥可以多把并存，这是路径 A 成立的前提：`official-keys.json` 是数组，`check:signature` 会按 `SIGNATURE` 的 keyId 找对应公钥验签。新增公钥只改这一个数据文件，不动任何逻辑代码。

## 三、公钥数据文件

`packages/shared/src/official-keys.json` 是官方公钥的**唯一真相源**：

```json
[
  {
    "keyId": "<公钥 PEM 的 sha256 前 32 位>",
    "pem": "-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----",
    "since": "YYYY-MM-DD",
    "label": "用途 / 设备名"
  }
]
```

- `trust.ts` 通过 `import officialKeys from './official-keys.json'` 导出 `OFFICIAL_PUBLIC_KEYS`（保持渲染层可安全引用，不引入 `node:crypto`）。
- `scripts/check-signature.mjs` 与 `scripts/init-signing-key.mjs` 直接 `JSON.parse` 该文件，不再正则解析 TS 模板字符串。
- `trust.test.ts` 逐把校验 `keyId` 与 `pem` 匹配、算法为 ed25519，防止手工填错。
- 追加/吊销公钥只改这个 JSON；`OFFICIAL_PUBLIC_KEYS` 数组本身不再在代码里手写。

## 四、新设备开箱步骤

```bash
# 1. clone 后直接验证（无需私钥）
pnpm install
pnpm verify          # 含 check:signature，验的是已入库的 .sshktool

# 2. 只有需要重新签发分发包时，才初始化本机密钥
pnpm keys:init
```

`keys:init` 会：
- 本机无密钥 → 生成 Ed25519 密钥对，私钥写入 `~/.sshk/official-signing-key.pem`（权限 600）；
- 本机已有 → 只展示，不覆盖（幂等）；
- 打印公钥 PEM、keyId，并检测是否已在 `official-keys.json` 登记；未登记时输出可直接粘贴的 JSON 条目（PEM 换行已自动转义）。

把打印出的条目追加到 `packages/shared/src/official-keys.json` 数组（填当天日期与用途），提交后即可用本机私钥签名：

```bash
node scripts/sign-tool.mjs template-tool
node scripts/pack-tool.mjs template-tool
pnpm verify
```

**登记前**用新密钥签出的包会被 `check:signature` 拒绝（公钥不可信），这是预期行为，不是 bug。

## 五、私钥来源优先级（`sign-tool.mjs`）

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `SSHK_ROTATE_SIGNING_KEY=1` | 轮换：生成新密钥对、落盘新私钥、打印新公钥；旧公钥保留，此前签发的包继续可信 |
| 2 | `SSHK_OFFICIAL_SIGNING_KEY` | PEM 文本（环境变量 / CI Secret），覆盖本机文件 |
| 3 | `~/.sshk/official-signing-key.pem` | 本机开发默认 |
| — | 三者都没有 | 明确报错并给出 `pnpm keys:init` 指引 |

## 六、安全红线

- **私钥绝不写入仓库任何路径**，包括 `secrets/`、`.tmp/`、`examples/`。`.tmp/` 会被清理，且历史上曾把私钥临时放这里，已迁移到用户级目录。
- **不通过聊天工具、邮件、明文网盘传输私钥**；路径 B 必须走公司密钥库/密码管理器。
- `.env` 已 gitignore；若用 `SSHK_OFFICIAL_SIGNING_KEY`，只写在本机 `.env` 或 CI Secret，不提交。
- 泄露处理：从 `official-keys.json` 移除对应条目（此后该密钥签的包不再被信任）→ 用 `SSHK_ROTATE_SIGNING_KEY=1` 生成新密钥 → 追加新公钥 → 重签并重发受影响的包。

## 七、常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `未找到官方签名私钥` | 新设备未初始化 | `pnpm keys:init` |
| `签名与内容不匹配` | 签名对象口径漂移或包被改过 | 重新走 `sign-tool` → `pack-tool`，勿手改包内文件 |
| `SIGNATURE keyId ... 不在 official-keys.json 中` | 新设备公钥未登记 | 按 `keys:init` 输出把 JSON 条目追加进数据文件并提交 |
| `该包申请 main 权限但包内没有 SIGNATURE` | 打包前漏签名 | 先 `sign-tool` 再 `pack-tool` |

## 八、相关约定

- 规范签名对象（canonical manifest + 其余文件哈希清单）见 `packages/shared/src/trust.ts` 头部注释，是唯一裁决方。
- 签名侧 `scripts/lib/tool-package.mjs::buildSignaturePayload`、验签侧 `apps/desktop/src/main/runtime-installer.ts::verifySignature`，由 `check:signature` 闭环校验。
- 环境变量双向契约见 `.env.example` 头部与 `scripts/check-env.mjs`。
